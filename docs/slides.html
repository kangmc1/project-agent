02문제

1. 배경

운영 로그에는 정답도 라벨도 없다

에이전트가 동작하는 과정에서는 다양한 이유로 응답에 오류가 생긴다. 어디서 시작됐고 어떤 유형인지를 탐지하고 수치화해야 하는데, 운영에서 남는 것은 실행 기록뿐이다.

대상 시스템

orchestrator가 과제별 subagent에게 일을 나누어 맡기는 순차 멀티에이전트 시스템. 2026년 프로덕션의 기본형인 orchestrator-worker 구조.

탐지의 조건

실행 중 저장된 기록 위에서, 실행이 끝난 뒤에 수행한다. 과제의 정답이나 사람이 단 라벨은 쓰지 않는다. 실행 도중 끼어드는 가드레일은 범위 밖.

기록에 담기는 것

스텝(모델 호출)마다 그 에이전트가 받은 메시지 전체, 응답, 부른 도구와 돌아온 결과. 에이전트별로 따로 쌓이며 그 사이를 오가는 것은 handoff 메시지와 공유 파일뿐.

04문제

1. 배경 · 문제 정의

오류는 스텝의 어느 자리에서 드러나는가에 따라 성격이 다르다

결정 → D1
결정의 불확실성

어느 subagent·도구를 부를지. 잘못된 위임, 건너뜀, 실패한 위임 반복. 기록에는 정상 호출 한 줄로만 남는다.

행동 → D2
행동의 근거

지시가 요구한 조회를 건너뜀, 기록에 없는 값으로 호출, 오류 반환. "요구된"과 "주어진"은 자연어에서 읽어야 한다.

보고 → D4
보고의 근거

근거에 없는 값(환각), 값은 맞는데 틀린 결론(추론 오류). 대조할 구조화 기록이 없고 모든 문장이 근거에 있어야 하는 것도 아니다.

스텝 사이 → D3
handoff의 정보 손실

지시가 전제로, 보고가 다음 행동으로 넘어갈 때 사실이 빠지거나 바뀜. 받은 쪽은 정상으로 움직여 오류가 뒤늦게 드러난다.

과제의 네 유형은 여기에 들어온다. handoff 문제는 결정과 경계, 도구 사용 실패는 행동, 환각은 행동(인자)과 보고, 추론 오류는 보고. 라벨도 이 자리에 맞춰 handoff / tool / reasoning_stability 세 범주로 단다.

05배경

2. 기존 연구 · 1.3 차별점

공개 벤치마크는 실패 트레이스의 출력만 남긴다

기존 연구
  • 실패 귀속 벤치마크 Who&When, TraceElephant. 실패 트레이스만, 확률은 다른 모델로 근사. 완전 관측이 필요하다는 결론은 공유.
  • 트레이스 오류 분류 MAST, TRAIL. 라벨 규약의 범주 정의의 바탕.
  • 불확실성 기반 탐지 semantic entropy, SelfCheckGPT. 샘플링 기반. 이 연구는 유한 행동 집합에서만 불확실성을 쓴다.
이 연구의 차별점
  • 결정의 불확실성을 실행 모델 자신의 확률로 잰다. 같은 가중치·템플릿·도구 스키마, 샘플링 없음.
  • 판정 주체를 층에 맞춘다. 결정·행동은 코드, handoff 경계는 LLM. 어느 층에 무엇이 맞는지를 데이터로 정했다.
  • 정답과 라벨 없이 돈다. 임계값도 자기 분포의 백분위.
  • 성공 실행을 포함한 완전 관측 데이터셋과 생성 파이프라인을 남긴다.

3. 제안 · 실행 환경

τ-bench airline을 orchestrator→subagent 그래프로 실행한다

고객(시뮬레이터, 같은 모델) ⇄ orchestrator ─┬─ policy_checker  (think 도구 + 시스템 프롬프트의 정책 문서)
                                             ├─ db_agent        (예약 데이터베이스 도구 14개)
                                             └─ read_file / write_file  (공유 파일 /case_notes.md)
왜 이 벤치마크인가

정책 판단과 데이터베이스 조회가 섞인 고객 응대 과제. 대화가 끝난 뒤 DB의 최종 상태가 정답과 같아야 성공이라 성패가 객관적이다.

subagent는 이름 있는 래퍼 도구

내장 task는 대상 subagent를 인자 안에 숨겨 "누구를 부르는가"의 확률을 잴 수 없다. 래퍼로 노출하면 handoff 결정이 D1이 채점할 수 있는 도구 이름 위치에 놓인다.

모델

실행 모델과 고객 시뮬레이터 모두 Qwen3-32B(thinking 끔). 같은 하네스로 돌린 AIME 2026 30회는 solver가 일을 거의 다 해 멀티에이전트 과제로 부적합, 부록 C.

3. 제안 · 기록과 운영 조건

완전 관측 기록 위에서, 라벨 없이

기록하는 것 (§3.2)
  • 스텝마다 HTTP 계층의 요청 본문(messages, tools 스키마)과 응답 본문(content, tool_calls, 생성 토큰의 logprob, finish_reason)
  • 어느 에이전트의 호출인지는 요청 헤더로
  • 도구 호출과 결과는 SQLite에, 공유 파일과 todo는 스텝별 스냅샷으로, 요약 직전 원문도
라벨 없는 운영을 위한 설계 (§3.4)
  • 탐지기 입력에 정답, 보상, 라벨이 없다. 임계값은 모듈별 자기 분포의 백분위

  • 전제는 완전 관측 로깅 계약. 출력만 남는 로그에서는 D1·D2·D3이 돌지 않는다

4.4 기대 효과

운영 로그를 사후 검토하는 제품에 그대로 얹힌다

  • 라벨 없는 순위와 근거 포인터. 첫날부터 스텝 순위가 나오고 검수자는 상위 몇 %만 연다. 순위 → 소량 검수 → 임계값 갱신의 닫힌 루프.
  • 트레이스가 아니라 시스템을 평가. 역할별·handoff 엣지별 프로파일이 프롬프트 수정, subagent 분리 같은 조치의 대상을 지목한다.
  • 로깅 계약이 곧 온보딩 체크리스트. 입력 전체, 응답, 도구 인자와 결과, 공유 상태 스냅샷, 에이전트 식별자, 그리고 D1을 위한 logprob 접근.
  • 라벨 없이 시작. 백분위 임계값으로 출발하고 검수가 쌓이면 그 셀만 라벨 최적으로 옮긴다.
  • 감사 가능. 결정·행동 층의 판정이 코드라 이의 제기에 근거 포인터로 답하고, 규칙 변경의 영향을 재실행으로 확인한다. LLM 판정은 D3 하나뿐이며 사실 목록으로 추적된다.

## 읽는 법
- 1~3번은 **원인**(오류가 생기고 굳는 메커니즘), 4번은 **그것을 못 보는 이유**, 5~7번은 **피해가 커지는 이유**, 8~10번은 **구조·조직** 문제다.
- 네 증거원이 모두 가리키는 것은 1, 2, 4, 5, 6번이다. 특히 **6번은 T(우리 데이터)와 P(실제 사고)가 정확히 같은 메커니즘을 지목**한다: 요약/압축 시점에 이미 틀어진 상태나 제약이 사실로 굳거나 사라지고, 원본이 없어 복구되지 않는다.
- 8번(멀티에이전트 조정)은 정의에 따라 3%에서 32%까지 흔들린다. 좁게 "에이전트 간 메시지 결함"으로 잡으면 작고, 넓게 "오케스트레이터가 책임인 실패"로 잡으면 크다. 단독 주제로 삼기엔 빈도 근거가 약하고, 1·2·6번의 전파 경로로 두는 것이 정직하다.
- 에이전트 특유(일반 LLM 아님): 1, 2, 5, 6, 7, 8. 환각·"거의 맞는" 코드·조직 통합은 기존 문제가 지속.

## 탐지 문제로 바꿀 수 있는 것 (아직 선택 아님)
- 2번: "완료·진행 선언이 상태와 맞는가" — false success / 미검증 진행 탐지. judge가 가장 못 잡는 영역, 프로덕션 로그(대화만 있어도) 적용 가능.
- 6번: "압축·요약을 거치며 제약·상태가 보존됐는가" — compaction 전후 대조. 실제 사고의 근본 원인, 우리 H3 파이프라인이 그대로 적용.
- 3번: "주장이 도구 관측에 근거하는가" — grounding 검사. 벤치마크 다수, 차별화는 멀티턴·사람 라벨.
- 4번: "탐지기 자체를 얼마나 믿을 수 있는가" — 정상 궤적 오탐, 절단 문맥 붕괴.
- 1번: "오류가 굳는 시점을 얼마나 일찍 잡는가" — 첫 오류 스텝·prefix 탐지. 벤치마크 최다 영역.

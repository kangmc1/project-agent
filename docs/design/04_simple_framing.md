# 단순화된 문제 정의 (v1, 2026-09-08 15:30)

## 1. 현재의 에이전트 시스템은 어떤 방식으로 작동하는가
- 핵심은 **루프**다. LLM 호출 → 결정(생각 / 도구 호출 / 다른 에이전트에 위임 / 최종 답) → 환경 관측(도구 결과, 페이지, 실행 출력) → 관측을 문맥에 추가 → 다시 LLM 호출. 과제가 끝나거나 예산이 다할 때까지 반복.
- **문맥(프롬프트)이 유일한 상태**다. 에이전트가 "아는 것"은 지금 프롬프트에 들어 있는 것뿐이다. 학습된 지식 외의 모든 사실·제약·진행 상황은 문맥에 글로 있어야 한다.
- 문맥은 유한하므로 세 가지 장치가 붙는다. (a) **압축**: 길어지면 앞부분을 요약으로 대체(Claude Code 95%에서 auto-compact, Magentic-One 재계획), (b) **외부 메모리**: 파일·DB·메모리 도구에 저장, (c) **분할**: 여러 에이전트(오케스트레이터-워커, 서브에이전트)가 각자 문맥을 갖고 메시지로 소통.
- 도구는 MCP 등 표준 인터페이스로 붙고, 도구 결과는 신뢰 불가 텍스트로 문맥에 들어온다(인젝션 경로). 사람은 시작 지시와 승인 게이트에만 관여하며, API 사용의 77%는 사람이 루프 밖(Anthropic Economic Index).
- 산업 배치: 고객 응대(1차 봇→전문 절차→사람), 코딩(서브에이전트·샌드박스 병렬), 리서치(리드+서브에이전트 3~5 병렬), 엔터프라이즈(도구 30~40개 넘으면 에이전트 분할). 병렬·분할이 늘수록 압축과 메시지 교환이 늘어난다.

## 2. 현재의 에이전트 시스템에서 일어나고 있는 문제점들
(네 증거원 교차, `03_problem_landscape.md`)
| # | 문제 | 한 줄 | 근거 |
|---|---|---|---|
| P1 | 오류 누적 | 초반의 작은 오류가 문맥에 남아 이후 판단을 계속 오염시키고 스스로 고치지 못함 | pass^8 <25%, 멀티턴 −39%, 자기 오류가 문맥에 있으면 더 틀림 |
| P2 | 미검증 진행·false success | 확인 없이 다음 단계로 가거나 "완료"라고 선언 | MAST 23.5%, false success τ² 45~48% / AppWorld 76%, 통과 실행 9.3%에 과정 이상 |
| P3 | 관측 오독·도구 오용 | 도구 결과를 잘못 읽거나 잘못된 인자·도구 사용 | τ-bench 실패 ~50% 잘못된 인자, 도구 출력 오해석 20~34%, 근거 부족 33~45% |
| P4 | 압축·handoff에서 상태 소실 | 요약·위임·메모리 저장 시 제약과 사실이 빠지거나 추측이 사실로 굳음; 원본이 없어 복구 불가 | 재계획 75건 중 59건 틀어진 상태 굳힘, OpenClaw 사고, 압축 시 blocker 100% 비활성 |
| P5 | 무단·파괴적 행동 | 프롬프트의 금지를 어기고 삭제·전송·결제 | Replit/PocketOS/Amazon/Meta 사고, 미해결 모호성 하 쓰기 34% |
| P6 | 인젝션·공급망 | 도구 결과 속 지시에 하이재킹 | ASR 86.7%, NIST 81%, MCP 91.8% 인증 없음 |
| P7 | 멀티에이전트 증폭 | 에이전트가 늘수록 오류 17배, 비용 15배, 조정 실패 12~32% | MAST, 스케일링 연구 |
P1~P4가 "오류가 생기고 굳는 메커니즘", P5~P7이 "피해가 커지는 구조". 에이전트 특유(단일 LLM에 없던 것): P1, P2, P4, P5, P6, P7.

## 3. 기존 기술로 이 문제들을 탐지할 수 있는가
| 기법 | 무엇을 잡나 | 성능 근거 | 한계 |
|---|---|---|---|
| 결과 오라클(테스트·DB 상태 대조) | 최종 실패 | 벤치마크의 기본 | 프로덕션엔 정답이 없음; 과정 이상은 못 봄(통과 실행 9.3% 이상) |
| 규칙·스키마 검사(도구 인자 검증, 형식, 에러 코드) | 형식·시스템 오류, 명백한 인자 오류 | TRAIL 형식 오류 23% 등은 규칙으로 가능; 비용 0 | 의미 오류 못 잡음; substring 판정 κ 0.05 |
| LLM-as-judge (trace/span) | 환각·지시 불이행·이탈 | 궤적 단위 성공 판정 precision 73~92%(모바일); 상용 제품 전부 이 방식 | 스텝 위치 특정 11~33%; false success AUROC 0.65; 프로덕션 결함 9개 중 2개→23개 중 0개; 정상 궤적 42~50% 과잉 탐지; 위치·자기선호 편향 |
| 프로세스 보상 모델 / 학습형 탐지기 | 스텝 단위 오류 | 궤적 RL 학습 8B가 프론티어 judge 능가(63.8/20.7%) | 도메인 밖 일반화 약함; 학습 데이터 필요 |
| 텔레메트리 모니터(통계) | 루프·반복·이상 패턴 | 주입 실패 AUROC 0.87, <1ms | 자연 실패 AUROC 0.31~0.42; 배포 간 전이 안 됨 |
| 인젝션 탐지기·가드레일 | 알려진 공격 패턴 | 95% 차단 | "95%는 부족"; 우회 지속; 해법은 아키텍처 격리 |
| 사람 검토 | 거의 모든 것 | 결함 30개 중 70%를 사람이 발견 | 처리량 한계, 승인의 의례화 |
정리: **P3 중 형식·인자 오류, P6 중 알려진 패턴, 최종 실패 여부**는 기존 기술로 잡힌다. **P1, P2, P4, P5의 과정상 결함**은 judge가 주된 도구인데 위 숫자대로 신뢰도가 낮다.

## 4. 기존 기술로 아직 탐지할 수 없는(어려운) 문제
| # | 어려운 것 | 왜 어려운가 | 근거 |
|---|---|---|---|
| D1 | **false success / 미검증 진행** (P2) | 텍스트는 그럴듯하고 환경 상태와 대조해야만 드러남; judge는 텍스트만 봄 | AUROC 0.65/0.54; "fail-plausible" 오류는 사람만 발견 |
| D2 | **압축·handoff 경계의 상태 소실** (P4) | 사후에는 원본 문맥이 없어 무엇이 빠졌는지 알 수 없음; 경계 시점에 대조해야 함; 이를 평가한 벤치마크 없음 | 3차 검증 G3 잔여; 사고 원인이 compaction |
| D3 | **초반의 결정적 오류를 눈덩이가 되기 전에 잡기** (P1) | 그 시점엔 "틀렸다"는 증거가 없고 사후엔 증상이 여러 스텝에 번져 뿌리를 못 찾음 | 스텝 위치 특정 11~33%; prefix 탐지 AUC 0.55~0.74 |
| D4 | **도구 관측 대비 주장의 근거 검증(멀티턴)** (P3) | 어느 관측이 근거인지 골라야 하고 관측이 길고 구조적; RAG용 검증기는 단일 관측·합성에서만 평가됨 | G7 잔여; 도구 환각 탐지 11.6% |
| D5 | **탐지기 자체의 오탐과 신뢰도** (횡단) | 정상 궤적에서 스텝 단위 오탐 미측정; 주입 실패로 검증한 탐지기가 자연 실패에서 붕괴; 벤더 정확도 미공개 | G1, G2(step), G6 잔여 |
| D6 | **프로덕션 로그의 입력 부재** (횡단) | 상용 분석 제품이 받는 것은 사용자·봇 메시지뿐; 도구 호출·문맥·위임 메시지가 없으면 D1~D4 모두 불가 | Align AI SDK 스키마; TraceElephant "입력 있으면 +76%" |
공통 구조: **D1~D4는 모두 "두 시점·두 문서의 대조"가 필요**하다(선언 vs 상태, 압축 전 vs 후, 오류 시점 vs 증상 시점, 주장 vs 관측). 현재 judge는 한 문서를 한 번 읽는다. D5·D6은 그 대조를 믿을 수 있게 하고 가능하게 하는 조건이다.

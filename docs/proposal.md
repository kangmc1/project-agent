# 안정성 기반 멀티에이전트 실패 탐지: 실행 모델의 logprob과 기록 대조로 handoff·도구·추론 실패를 사후 감사하는 파이프라인

> 콕스웨이브 AI 리서치 및 제품화 엔지니어 직무과제 제출 문서 (2026-09-09)
> 코드: https://github.com/kangmc1/project-agent · 발표 슬라이드: `docs/slides.html`

## 0. 한 문장 요약

멀티에이전트 실패는 **불안정성**으로 드러난다. 순차 오케스트레이션에서 "다음 행동"은 유한 집합이므로 실행 모델의 실제 logprob으로 그 분포를 샘플링 없이 직접 계산하면 handoff·도구 선택의 불안정을 재고, 환각과 추론 오류는 "결론의 안정성" 하나로 묶어 **기록 대조**(출처·충실도·재도출)로 검사한다. 탐지기는 정답도 라벨도 쓰지 않는 **오프라인 감사 멀티에이전트**이며, 성공·실패 트레이스를 함께 실행한 실험으로 오탐율과 회복 여부까지 측정한다. 주 실험인 τ-bench airline 30회에서 이 가설은 **planner 결정에서 성립**했고(decisive 스텝 AUROC 0.75 [0.61, 0.86], 전체 오류 0.63 [0.54, 0.71], 트레이스 수준 max 0.81) subagent에서는 성립하지 않았으며(그 층은 행동 근거성 검사 D2 — 도구 호출이 기록이 요구하고 허용한 것인가 — 가 부분적으로 맡는다: clean 스텝의 7 %를 잘못 울리며 subagent 오류의 절반을 잡음, F1 0.54, precision 0.62, recall 0.48; AUROC 0.70 [0.63, 0.78]), 탐지기 성능은 항목보다 **역할 배정**에 의해 갈렸다(§4.2 핵심 결과). AIME 2026 30회는 보조 실험이다 — 수학 풀이는 subagent 하나가 거의 전부를 하는 구조라 멀티에이전트 과제로 부적합함이 이 규모에서 관찰됐다(§4.2.12).

## 1. 배경 (Background)

### 1.1 연구 세부 주제

- 대상: planner(오케스트레이터)가 task-specific subagent에게 일을 넘기는 **순차 멀티에이전트 시스템**(LangChain Deep Agents 하네스로 구성) — 2026년 프로덕션의 기본형인 orchestrator-worker 구조.
- 상황: **오프라인 사후 감사**. 운영 중 쌓인 실행 기록(모델이 실제로 본 입력, 출력, 도구 호출/결과, 공유 파일)을 나중에 훑어 실패를 탐지·위치 귀속하는 파이프라인. 실시간 개입(가드레일)은 범위 밖.
- 질문: 정답(ground truth)도 사람 라벨도 없는 운영 환경에서, **기록만으로** 어느 스텝에서 어떤 종류의 실패가 났는지 짚어낼 수 있는가? 그 판단의 근거를 사람이 검수할 수 있는 형태로 낼 수 있는가?

### 1.2 현재 에이전트 시스템의 문제 정의

미션이 나열한 네 유형을 이 시스템의 어디에서 관찰할 수 있는지로 다시 정의한다.

| 미션 유형 | 이 제안의 범주 | 어디서 관찰되나 | 이 제안의 검사 |
|---|---|---|---|
| handoff 문제 | **handoff 불안정** | planner가 어느 subagent를 부를지 결정하는 지점; 지시→전제, 보고→인용 경계 | D1(handoff 층) + D3 |
| 도구 사용 실패 | **행동 근거성** | subagent가 handoff 안에서 부른(또는 부르지 않은) 도구와 그 인자가 기록이 요구·허용한 것인가 | D2(행동 근거성 — 세 어긋남: 기록이 요구한 호출을 하지 않음 ∪ 기록에 없는 값으로 호출 ∪ 호출이 성립하지 않음) + D1(도구 층, planner) |
| 환각 | **추론 안정성** (통합) | 도구 호출 인자의 값이 에이전트에게 주어진 기록에 있는가 | D2 어긋남 (2)(기록에 없는 값으로 호출)와 그 증상인 (3′). **발언 속 값·결론의 근거 층은 탐지기가 없다**(D4는 설계만, §3.3) |
| 추론 오류 | **추론 안정성** (통합) | 결론이 근거로부터 재도출되는가 | D3(경계 왜곡)만. **값은 맞는데 결론이 틀린 추론 오류 층은 이 연구에 탐지기가 없다**(§4.3) |

환각과 추론 오류를 하나로 묶은 이유: (1) 스텝 시점에서 "지어낸 값"과 "잘못 계산한 값"은 구분되지 않는 경우가 많고 사람 어노테이터의 일치도도 낮다(MAST, Who&When의 세부 유형 κ), (2) 운영상 중요한 것은 "이 결론을 믿어도 되는가"이며 원인 분류는 사후 태그로 충분하다, (3) 두 유형 모두 "근거로 지지되지 않는 결론이 궤적에 유입된다"는 하나의 사건이다.

### 1.3 차별점 (Novelty)

1. **실행 모델의 실제 logprob으로 유한 행동 집합 위의 분포를 계산한다.** 공개 트레이스 벤치마크(Who&When, TraceElephant)는 GPT-4o 출력만 남아 프록시 모델로 재생해야 하지만, 우리는 실행과 채점에 같은 가중치·같은 템플릿·같은 도구 스키마를 쓴다. 샘플링이 필요 없고, 결정 지점당 후보 수만큼의 짧은 채점으로 끝난다(§3.3).
2. **환각·추론을 "결론 안정성"으로 통합하고 판정은 코드가 한다.** LLM은 handoff 경계의 발언을 atomic fact로 바꾸는 추출기(D3)로만 쓰고, 옳고 그름은 기록 검색·집합 비교가 결정한다. LLM-judge와 달리 근거 포인터(어느 스텝의 어느 도구 결과와 어긋났는지)가 항상 붙는다.
3. **탐지기는 정답·라벨을 입력으로 받지 않는다.** 임계값도 자기 분포의 백분위로 정하고, 라벨은 우리 실험의 평가에만 쓴다. 이것이 Align류 운영 솔루션에 바로 얹힐 수 있는 조건이다.
4. **성공 트레이스가 있다.** 귀속 벤치마크(실패 트레이스만)로는 잴 수 없는 오탐율·회복(transient vs decisive) 분석이 가능하다.

## 3. 제안 (Methodology)

### 3.1 실행 환경: Deep Agents 위의 두 그래프

```
[τ-bench airline]                                   [AIME 2026]
 customer(user_sim) ⇄ planner ──policy_checker──▶ think, 정책 wiki      planner ──solver──▶ run_python
                          └──db_agent──▶ 14 DB 도구                          └──verifier──▶ run_python (독립 재계산)
                     공유 FS: /case_notes.md (subagent가 append)               submit_answer
```

- subagent는 **이름을 가진 래퍼 도구**(`policy_checker`, `db_agent`, `solver`, `verifier`)로 planner에 바인딩된다. deepagents의 내장 `task` 도구는 대상 subagent를 인자(`subagent_type`, 자유 텍스트 뒤)에 두어 D1이 잴 수 없기 때문이다. 래퍼는 내장 `task`의 state 규약(copy-in/merge-out)을 복제해 공유 FS를 유지한다.
- 실행 모델 Qwen3-32B(vLLM, thinking off), 사용자 시뮬레이터도 같은 모델. 요약 미들웨어는 16k 토큰에서 명시 발동.
- **주 실험은 airline이다.** AIME 그래프는 결과 검토 후 보조 실험으로 내렸다: solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적어(라벨된 planner 오류 6건) planner→subagent 분해가 형식적이었다(§4.2.12).

### 3.2 완전 관측 기록

스텝(=LLM 호출)마다 HTTP 계층에서 요청 본문(messages, tools 스키마)과 응답 본문(content, tool_calls, 생성 토큰 logprobs, finish_reason)을 그대로 저장하고, 에이전트는 요청 헤더로 귀속한다. 도구 호출/결과는 SQLite, 공유 FS/todo는 스텝별 스냅샷, 요약 직전 원문도 보존한다. 이것이 탐지기의 **유일한 입력**이다.

### 3.3 감사 멀티에이전트(auditor): 모듈 정의

Dn은 감사 MAS의 탐지기(detector) 모듈 번호다. 설계 인터뷰의 점검 차원 번호에서 출발했으나 최종 문서에서는 결과에 쓰인 순서로 다시 붙였다(D1 결정, D2 행동, D3 handoff; D4는 설계만). 설계만 남긴 선택 모듈 D6·D8·D10은 원래 번호를 유지한다. 네 모듈은 각각 기록의 다른 층을 다른 상대와 대조한다. 한 줄씩 정리하면 다음과 같다.

| 모듈 | 대상 | 대조 상대 | 판정 주체 | 한 문장 |
|---|---|---|---|---|
| D1 | 행동 선택 | 모델 자신의 확률 분포 | 코드 | 결정이 얼마나 흔들렸나 |
| D2 | 행동(도구 호출) | 기록(지시문·주어진 값) | 코드 | 한 행동이 기록이 요구하고 허용한 것인가 |
| D3 | handoff 텍스트 | 경계 반대편 텍스트 | LLM 추출 + 코드 | 넘기는 과정에서 무엇이 빠졌나 |
| D4 [설계만] | 발언 | 근거(도구 결과·지시문) | 외부 LLM | 말한 것이 근거에 얼마나 의존하나 |

D4와 D2는 같은 기록을 놓고 한쪽은 **말**을, 한쪽은 **행동**을 대조한다. 행동(도구 호출)은 구조화 JSON이라 코드로 대조할 수 있고, 발언은 자연어라 LLM이 필요하다. 이번 결과에서 코드 대조(D2)는 정밀하게 작동했고 LLM 대조(D4)는 8B로는 실패했다는 것이 두 모듈의 대비다(§4.2, §4.3).

```
기록(steps.jsonl · tool_calls.sqlite · fs/) → 스텝 = [결정] → [행동: 도구 호출] → [발언]  (+ 스텝 사이의 handoff 경계)

 층            탐지기  검사                                                              대상            판정 주체
 ─────────────  ──────  ────────────────────────────────────────────────────────────────  ──────────────  ─────────
 결정          D1      후보 행동 위 분포: 1−p_actual · 1−confidence · 1−margin           planner·subagent 코드(LLM 없음)
                       + handoff 층(subagent에 넘길지 말지의 이진 엔트로피)              planner
 행동(도구)    D2      행동 근거성 플래그(0/1): (1) 기록이 요구한 호출을 하지 않음          주로 subagent   코드(LLM 없음)
                       ∪ (2) 기록에 없는 값으로 호출 ∪ (3′) 호출이 성립하지 않음(오류 반환;
                       파일 도구 첫 read·래퍼 행 제외)   [결과 처리 검사는 정의 밖]
 handoff 경계  D3      지시→전제 · 보고→planner: atomic facts 보존도(fidelity)            planner↔subagent 8B 추출 + 코드 집합 비교
 발언·추론     D4      [설계만 · 결과 미사용] 근거(도구 결과+지시) vs 응답의 주장별 관계  subagent        LLM 판정 (8B 파일럿 부적합)

 출력: 항목별 플래그 + 근거 포인터 → 트레이스 보고서(P4b) → 시스템 집계(P4c). 통합 점수 없음.
```

결과에 쓰인 모듈은 D1·D2·D3 셋이다. 설계만 하고 결과에 쓰지 않은 모듈: D4 근거 의존 판정(아래), D8 축약 손실(요약 전후 atomic facts), D10 계획-행동 일치(todo/ledger vs 실제 호출), D6 재도출(정책 규칙 코드/재계산). 판정 주체 구분: **D1·D2 = 코드형**(LLM을 쓰지 않음), **D3 = 에이전트+코드**(8B가 발언을 atomic fact로 구조화, 판정은 코드), **D4 = LLM 판정**(설계만).

**D1 — 행동 분포 confidence.** 결정 지점 = assistant 스텝. 후보 집합 A = 그 스텝에 바인딩된 도구 이름 ∪ {no_tool}. 정의: 렌더된 prefix를 고정하고 action 토큰만 바꿔 넣어 log P(a | context)를 얻는다(`<tool_call>\n{"name": "a`; 닫는 따옴표는 모델이 `",`를 한 토큰으로 내므로 제외). 실행: 같은 값을 `allowed_token_ids=[tᵢ]`로 강제한 1토큰 생성의 raw logprob 곱으로 계산해 prefix cache를 유지한다(§4.1에서 두 방식의 동일성 검증). 출력: 분포, 엔트로피 H, confidence = 1 − H/log|A|, p_actual, 1–2등 마진, 그리고 **2층 보고**(도구 층: 전체 A / handoff 층: {위임 래퍼} vs {비위임} 재정규화).

**D2 — 행동 근거성(action grounding), 절차형.** 질문은 하나다: "이 행동(도구 호출)은 기록이 요구하고 허용한 것인가". D4가 발언을 근거에 대조한다면 D2는 같은 대조를 행동에 한다. 한 질문의 **세 가지 어긋남** 중 하나라도 성립하면 스텝(비보조)에 1, 아니면 0을 돌려준다 — 규칙의 나열이 아니라 한 질문의 세 증상이다. **(1) 기록이 요구한 호출을 하지 않았다** — handoff마다 planner 지시문이 요구하는 도구 군(조회·검색·예약·변경·취소·계산·가격 등 airline 12군; AIME는 `run_python`)을 정규식으로 뽑아, 그 subagent가 handoff 안에서 실제로 부른 도구와 대조하고 하나라도 빠지면 subagent의 보고 스텝(마지막 스텝)에 붙인다(`src/audit/d2_instruction.py`). **(2) 기록에 없는 값으로 호출했다** — 스텝의 도구 호출 인자에서 식별자형 값(예약번호·사용자ID·편명·ISO 날짜·금액·출발/도착 공항 코드·이름)을 뽑아, 그 값이 에이전트에게 주어진 것(그 요청의 system/user/tool 메시지, 이전 고객 발화; 공항은 도시명, 날짜는 자연어 표기 허용)인지 확인한다. 인자는 구조화 JSON이라 LLM 추출이 없다(`src/audit/d2_args.py`). **(3′) 호출이 성립하지 않았다** — 그 스텝의 도구 호출이 오류를 돌려줬다. 단, 파일 도구의 오류(아직 만들어지지 않은 사건 기록 파일을 처음 읽는 `read_file`은 설계상 실패한다)와 래퍼 행의 오류(subagent 단위 오류는 subagent 자신의 스텝에서 판정한다)는 제외한다. (3′)는 대부분 (2)의 증상이다 — 기록에 없는 값으로 부른 호출이 "user not found"로 돌아오는 식이라, airline에서 (3′)가 걸린 subagent 스텝 57개 중 32개가 (2)와 겹친다. 그래도 (2)의 식별자 패턴이 놓친 잘못된 인자를 도구 쪽 실패로 잡아 주므로 정의에 넣었다(사용자 결정; 변형 비교는 §4.2.2). 합성은 `src/audit/d2_action.py`, 출력 `audit/d2_action.jsonl`; 플래그마다 어느 어긋남이 왜 걸렸는지의 근거 문자열이 붙어 트레이스 보고서로 간다. **정의에서 뺀 것**: (a) 발언의 숫자 주장에 도구 근거를 요구하던 규칙(발언 층의 문제라 D2의 질문이 아니고, 정당한 무도구 보고를 절반 이상 오탐), (b) 도구 호출 **결과의 처리**에 관한 로그 검사(empty · repeat · schema · ignored) — "결과를 잘못 다뤘나"는 로그 흐름만으로는 판정할 수 없다(§4.2.9). 결과 검토 과정에서 조건을 "규칙 1/2/3"이라 부르며 각각 따로 AUROC를 매겼으나, 이진 검사를 따로 순위 지표로 평가하는 것은 잘못이라(§4.1.4) 하나의 절차형 모듈로 재정의했다(부록 A.19).

**D3 — handoff 충실도.** 두 방향: 보고→planner 인용(subagent 보고의 atomic facts vs planner 다음 발언/행동 인자), 지시→전제(planner 지시 vs subagent 첫 발언의 전제 선언). 집합 차로 누락·추가·왜곡·fidelity.

**D4 — 근거 의존 판정 [설계만 · 결과 미사용].** subagent 응답이 자기 근거에 실제로 의존하는지를 LLM이 말로 판정하고 구조화한다. 판정 모델은 (A) 그 요청에서 subagent가 받은 근거(도구 결과 + planner 지시문)와 (B) subagent의 응답, 두 텍스트를 받아 응답을 원자 주장으로 나누고 주장마다 관계를 `supported`(근거에 그대로 있음) / `derived`(근거 값에서 계산·환산·요약됨) / `unsupported`(근거·지시에서 얻을 수 없음) / `contradicted`(근거와 충돌)로 표기한 JSON을 낸다. 스텝 점수 = (unsupported + contradicted) / 주장 수. 이 모듈에서는 LLM이 **판정자**다 — "LLM은 추출만, 판정은 코드"라는 이 제안의 원칙에서 의도적으로 벗어난 설계이며, 발언 층("값은 맞는데 결론이 틀림")을 잡을 유일한 후보라 남긴다. Qwen3-8B로 돌린 파일럿은 판정 신뢰도가 부족해 결과에 쓰지 않았다(§4.3 한계, 부록 A.20; 코드 `src/audit/unused/d4_judge.py`).

### 3.4 라벨 없는 운영을 위한 설계

- 탐지기 입력에 정답·reward·라벨이 없다. 임계값은 항목별 자기 분포의 백분위(상위 5/10%).
- 모든 플래그에 근거 포인터가 붙어 사람 검수 루프(순위 → 소량 검수 → 임계값 갱신)에 들어간다.
- 전제 조건: **완전 관측 로깅 계약**(도구 결과, 모든 메시지, 모델이 실제 본 입력, 실행 모델 logprob 접근). 출력만 남는 로그에서는 D1·D2·D3이 동작하지 않는다.

#### 4.1.4 지표 정의

| 지표 | 정의 | 모집단 |
|---|---|---|
| 스텝 AUROC | 항목 점수 × 역할(planner / subagent / all) × 도메인. 양성 = {decisive, transient, error}("전체 오류")와 {decisive}를 별도로. 음성 = clean. 95% CI = 층화 부트스트랩 1000회(seed 0), 동점은 평균 순위 | 라벨된 런의 비보조 스텝, 항목 점수 NA 제외, **cascade 제외** |
| 트레이스 AUROC | 런 단위 max/mean 점수 vs `success=false` | 역할 스코프 내 스텝의 항목 **채점률 ≥ 80%**인 런만. 도메인별 성공 <3 또는 실패 <3이면 "산출 불가" |
| 귀속 정확도 | 예측 decisive = 역할 스코프 내 argmax(동점은 planner 우선 → 이른 스텝). **정확 일치 / ±1**(비보조 스텝 순서 기준) **/ 에이전트 일치** | decisive_step이 있는 실패 런 |
| recall@FPR10 | 같은 역할·도메인의 clean 스텝에서 FPR ≤ 10%가 되는 최소 임계값에서의 recall. 실제 달성 FPR을 병기한다(이산·동점 항목은 정확히 10%에 닿지 못한다) | 스텝 AUROC와 동일 |
| 탐지 지연 | decisive 이후 임계값을 처음 넘긴 스텝까지의 거리(중앙값)와 `n_crossed/n_failed` | 실패 런 |
| 임계값 실험 | 라벨 없는 백분위(p95 = 상위 5%, p90 = 상위 10%; 풀 = `runs/index.csv` 전 런의 채점된 스텝) **vs 라벨 최적**(Youden J 최대). 행마다 recall·FPR과 최적 대비 차 | `eval/thresholds.md` |
| 회복 궤적 | transient 오류 전후, decisive 전후의 항목 점수 평균 궤적 | `eval/recovery.png` |
| 매칭 부표 | 모든 항목이 동시에 채점된 스텝의 교집합에서 AUROC 재계산 — 항목마다 모집단이 달라 생기는 비교 왜곡 제거 | `eval/metrics.md` §matched |
| subtag 서술 분석 | 라벨 subtag별로 어느 항목이 반응했는지의 분포. **환각/추론 개별 판정은 하지 않는다**(§1.2) — subtag는 사후 서술용 태그다 | `eval/subtags.md` |

**D2의 평가 단위는 모듈이고, 지표는 플래그에서 잰다.** D2는 세 어긋남의 OR로 0/1 하나를 돌려주는 절차형 검사이므로 어긋남별로 AUROC를 따로 매기지 않고(이진 점수의 AUROC는 (recall + 1 − FPR)/2로 결정되어 재현율이 낮은 고정밀 검사를 체계적으로 불리하게 읽는다), 그 플래그에서의 **precision · recall · F1 · FPR**과 decisive 재현율로 평가한다(`eval/metrics.md` §1b). F1 = 2·precision·recall / (precision + recall). AUROC는 연속 점수 항목(D1·D3)과 같은 표에 놓기 위한 참고값이다. 어긋남별 기여는 같은 셀에서 조건을 하나씩 더해 가며 플래그 지표가 어떻게 움직이는지로 보인다(§4.2.2). 모듈을 넘는 통합 점수(예: D1 + D2)는 내지 않는다. any-flag는 서술로만 보고한다. 정의는 `src/eval/{metrics,thresholds,recovery}.py`의 모집단 주석과 일치한다.

#### 4.1.5 D1 채점 방법과 타당성 검증

D1의 확률 `P(a | 문맥)`은 실행 후 같은 가중치(Qwen3-32B, 채점 전용 서버)로 **teacher-forced 재채점**하여 얻는다. 실행 기록에는 모델이 실제로 고른 행동의 logprob만 남고 나머지 후보의 값은 없기 때문이다. 후보 a의 토큰열은 `<tool_call>` 헤더 6토큰 + 이름 1~5토큰(7~11토큰)이며, 확률은 그 체인 전체 `∏ P(t_i | 문맥, t_<i)`다.

**채점 경로는 decode 경로다** (코드명 `stepwise`, `src/audit/d1.py`): 렌더된 prefix를 토큰 ID 배열로 고정하고, 후보 토큰을 한 개씩 `allowed_token_ids=[t_i]`로 강제한 1토큰 생성(`max_tokens: 1`)의 raw logprob(마스킹 전)을 읽어 합한다. 이 경로는 실행 시 모델이 토큰을 생성한 경로와 같고, vLLM prefix cache가 유지되어 호출당 마지막 토큰 한 step만 계산한다. `no_tool`은 첫 위치의 `1 − P(<tool_call>)`이다. 후보들의 공통 토큰 접두(헤더, 겹치는 이름 앞부분)는 한 번만 묻고 재사용한다(trie). 헤더 5토큰의 logp 합은 기록 974건에서 중앙값 −3×10⁻⁶, 최소 −0.0024로 무시할 수 있고, 실질적인 결정은 `<tool_call>` 여부와 이름 토큰에서 일어난다.

**재채점값 자체가 측정값이다.** 실행 시 기록된 logprob은 같은 가중치의 또 다른 bf16 계산 결과이므로 재채점보다 "참"에 가깝지 않고, 둘의 차이는 정확도가 아니라 두 추정치 사이의 반올림 잡음이다. 따라서 기록 logprob은 결과 지표로 쓰지 않고, **렌더 정합 검사**에만 쓴다: 결정 지점마다 기록의 생성 토큰열에서 `<tool_call>` 위치를 찾아 그 뒤 토큰열이 실제 선택 후보의 토큰열과 일치하는지 확인하고(불일치나 수 단위의 logp 이탈은 채팅 템플릿·도구 스키마 렌더 버그를 뜻한다), 정합 비율 한 줄만 보고한다. 실행 시 `logprobs` 옵션은 생성 토큰 ID를 받기 위한 채널로 켜 둔다(vLLM 0.9.2에는 `return_token_ids`가 없다). 결정 지점은 모델이 실제로 생성한 토큰열 위에 놓이며, 기록된 logprob 값 자체는 쓰지 않는다. 기록이 없는 실행은 응답 텍스트를 다시 토큰화한다(60회 검사에서 토큰 ID 완전 일치 467/471). 같은 요청도 prefix KV 블록이 다시 계산되는 시점에 따라 logp가 약 0.002(고확률 토큰), confidence가 약 0.005 흔들리는 **재현성 하한**이 있으며(같은 캐시 상태에서는 완전히 재현됨), 이것이 D1 값의 유효 자릿수다.

설계 초기에는 prefill 경로(`prompt_logprobs`, 코드명 `m2`)를 정의로 두고 decode 경로와의 분포 일치(|Δp| ≤ 0.01, 95%)를 게이트로 삼았다. 배치 1 검사에서 두 경로의 일치는 62%였으나, prefill 경로 자체도 기록 logprob과 같은 크기로 어긋났다(133지점, 확률 0.01 이내 86.5%, 최대 0.09). 즉 게이트가 잰 것은 두 재채점 경로 사이의 bf16 반올림 차이였고, 어느 경로도 다른 경로의 기준이 될 수 없다. 그래서 게이트를 철회하고 decode 경로 단일 방법으로 확정했다(사용자 결정, 09-09 04:12). prefill 경로 부분 채점(211지점)은 비교 표본으로만 남긴다(`audit/d1_m2_partial.jsonl`).

후보 집합 A = 그 스텝 요청 본문의 `tools` 이름 ∪ `{no_tool}`. 모델이 바인딩되지 않은 이름을 호출한 경우(환각 도구 이름)에는 그 이름을 **사후에 A에 추가해** 채점한다 — 그러지 않으면 실제 행동의 확률이 정의되지 않는다. `user_sim`·`summarizer` 스텝은 결정 지점이 아니다. 채점 서버의 24576 토큰을 넘는 prefix는 `d1_unscored.json`의 `prefix_too_long` 버킷으로 빠진다.

### 4.2 결과

#### 핵심 결과 (요약)

이 절의 결론은 세 문장이다. 아래 소절들은 이 세 문장의 근거와 상세이며, **본문 수치는 모두 주 실험 τ-bench airline(30회)**의 것이다. AIME 2026(30회)은 보조 실험으로 §4.2.12에 따로 둔다. 여기서 쓰는 두 용어만 먼저 적는다: **AUROC**는 오류 스텝과 깨끗한 스텝을 무작위로 하나씩 뽑았을 때 오류 스텝의 점수가 더 높을 확률(0.5 = 우연, 1 = 완벽)이고, **decisive 스텝**은 실패한 실행마다 라벨러가 하나 지목한 "실행을 실패로 이끈 스텝"이다. 나머지 용어는 §4.2.0.

| 모듈 | 층 | 역할 | 주 지표 | AUROC 전체 오류 / decisive (비교용) | 판정 |
|---|---|---|---|---|---|
| D1 결정 분포 | 결정 | planner | AUROC 0.63 [0.54, 0.71] / decisive **0.75** [0.61, 0.86] (1 − p_actual) | 좌동 | 작동 |
| D1 결정 분포 | 결정 | subagent | AUROC 0.54 / 0.36 | 좌동 | 신호 없음 |
| D2 행동 근거성 | 행동 | subagent | **F1 0.54** (정밀도 0.62, 재현율 0.48, FPR 0.07) | 0.70 [0.63, 0.78] / 0.59 | 작동 (부분) |
| D3 handoff 충실도, 보고→planner | 경계 | planner | AUROC 0.59 [0.47, 0.72] / 0.60 | 좌동 | 약함 |

주 지표는 모듈의 점수 형태에 맞춘다: 연속 점수(D1·D3)는 AUROC, 0/1 플래그인 D2는 F1·정밀도·재현율·FPR이다 — 이진 점수의 AUROC는 (재현율 + 1 − FPR)/2로 정해지는 값이라 재현율이 낮은 고정밀 검사를 체계적으로 불리하게 읽으므로, D2의 AUROC는 다른 모듈과 나란히 놓기 위한 비교용 열에만 둔다. 행 순서와 층 이름은 §3.3의 모듈 표와 같다.

**1. planner의 결정 불안정(D1)은 실패를 예고한다.** planner가 "다음에 누구를, 어느 도구를 부를지" 고른 지점에서 실행 모델의 확률 분포를 재계산하면, 실제로 실행된 행동의 확률이 낮았던 결정(1 − p_actual)이 decisive 스텝을 깨끗한 스텝과 **0.75** [0.61, 0.86]로 구별한다. 전체 오류 스텝에 대해서는 0.63 [0.54, 0.71]이다. 실행 단위로 보면, 실행 하나에서 가장 뜻밖이었던 결정 하나의 크기가 실행 성패를 0.81 [0.63, 0.96]로 가른다(성공 실행 6건, §4.2.3).

**2. subagent 층은 D1이 아니라 행동 근거성 검사(D2)가 맡고, 발언 층은 비어 있다.** subagent의 실수는 "어느 도구를 부를까"의 흔들림이 아니라, 확신을 갖고 지어낸 값으로 도구를 부르거나 확신을 갖고 시킨 조회를 건너뛰는 것이라 D1에는 보이지 않는다(decisive AUROC 0.36). D2는 "이 도구 호출은 기록이 요구하고 허용한 것인가"의 세 어긋남 — (1) 기록이 요구한 호출을 하지 않음, (2) 기록에 없는 값으로 호출, (3′) 호출이 성립하지 않음(오류 반환) — 중 하나라도 걸리면 1을 주는 절차형 검사이고, airline subagent 스텝에서 **clean 스텝의 7 %를 잘못 울리면서 라벨된 오류의 절반(23/48)을 잡는다** — F1 0.54(정밀도 0.62, 재현율 0.48). 정밀한 부분은 (2)와 (3′)다 — (2)만 켜면 플래그의 82 %, (3′)만 켜면 93 %가 실제 오류이고 (3′)는 대개 (2)의 증상(지어낸 값으로 부른 호출이 오류로 돌아옴)이다; 잡음의 대부분은 (1)의 지시문→도구 매핑에서 온다. 즉 D2는 단독 탐지기가 아니라 **정밀도 지향의 부분 검사**다. handoff 경계의 값 보존(D3)은 약했고 지시→전제 방향은 가설과 반대다. **값은 기록에 있는데 결론이 틀린 오류(발언·추론 층)는 이 연구의 어느 검사도 잡지 못하며**, 그 층을 위해 설계한 D4(LLM 근거 의존 판정)는 8B 파일럿에서 판정 신뢰도가 부족해 결과에 쓰지 않았다(§4.3). 이것이 남은 가장 큰 미해결 항목이다.

**3. 탐지기 성능은 탐지기 자체보다 "어느 역할·어느 층에 붙였나"로 갈린다.** 같은 D1이 planner에서 0.63–0.75, subagent에서 0.5 아래이고, 반대로 D2는 subagent에서 F1 0.54, planner에서는 플래그가 2건뿐이다. 보조 실험(AIME)은 이 대비를 도메인 축으로 다시 보여 준다: 같은 planner D1이 트레이스 수준에서 airline 0.81, AIME 0.34로 뒤집히고, 같은 반복 호출 로그 검사가 AIME 정밀도 0.86, airline 0.22다(§4.2.12). 감사 파이프라인은 모든 스텝에 모든 항목을 돌리는 구조가 아니라, 역할과 층(그리고 도메인)에 항목을 배정하는 라우팅으로 짜야 한다(§4.3).

배경: 주 실험 airline 30회(성공 6, 실패 24; 라벨 오류 이벤트 215, decisive 24), 라벨은 평가에만 사용, 탐지기는 라벨·정답을 입력으로 받지 않는다. 임계값을 고정하는 알람으로는 D1이 약하고(라벨 최적 임계가 측정 잡음 수준), 순위 지표와 검토 우선순위로 쓰는 것이 맞다(§4.2.6, §4.3). 보조 실험 AIME의 결과와 두 도메인 합산 수치는 §4.2.12.

#### 4.2.0 용어

아래 표들에 쓰는 용어를 먼저 정리한다. 지표의 계산 정의와 모집단은 §4.1.4에 있으므로 여기서는 읽는 데 필요한 뜻만 적는다.

- **결정 지점**: planner 또는 subagent가 다음 행동을 고른 스텝 하나. `user_sim`·`summarizer` 스텝은 제외.
- **후보 집합 A**: 그 스텝에 바인딩된 도구 이름들 + `no_tool`. 모델이 호출한 이름이 A에 없으면 사후에 추가한다.
- **dist**: A 위의 정규화 확률. 후보별 토큰열의 조건부 확률을 정규화한 것(§4.1.5).
- **p_actual**: dist에서 실제로 실행된 행동의 확률. **1 − p_actual**은 "실제 선택이 얼마나 뜻밖이었나".
- **confidence**: 1 − (dist의 엔트로피 / log₂|A|). 분포가 한 후보에 몰리면 1, 균등이면 0. 분산이 아니라 정규화 엔트로피다. **1 − confidence**는 "분포가 얼마나 퍼졌나".
- **margin**: dist의 1등 − 2등. 점수는 **1 − margin**.
- **handoff 층 (D1_handoff)**: planner의 결정 지점에서 dist를 "subagent에 넘긴다(래퍼 호출)" vs "그 외(직접 도구·`no_tool`)"의 둘로 합친 뒤 계산한 이진 엔트로피 H2. "넘길지 말지"의 불확실성이며, 누구에게 넘기는지는 보지 않는다.
- **D2 (행동 근거성 플래그)**: 스텝마다 0/1. "이 행동(도구 호출)은 기록이 요구하고 허용한 것인가"의 세 어긋남 — (1) planner 지시가 요구한 도구 군을 handoff 안에서 부르지 않고 끝냄(보고 스텝에 부여), (2) 도구 호출 인자에 에이전트에게 주어지지 않은 식별자형 값이 있음, (3′) 도구 호출이 오류로 돌아옴(파일 도구 첫 읽기·래퍼 행 제외) — 중 하나라도 성립하면 1. 결과 처리(반복·무시·빈 결과)는 정의에 들어가지 않는다. **플래그 지표**: precision = 1인 스텝 중 오류 비율, recall = 오류 스텝 중 1인 비율, **F1** = 둘의 조화평균, FPR = clean 스텝 중 1인 비율.
- **오류 이벤트**: 라벨러가 표시한 스텝 단위 오류(decisive / transient / error 세 클래스). 한 실행에 여러 개 있을 수 있다.
- **decisive 스텝**: 실패한 실행마다 라벨러가 하나 지목한 "실행을 실패로 이끈 스텝". **cascade 스텝**(decisive 이후 그 결과로 따라 나온 스텝)은 양성·음성 어디에도 넣지 않는다.
- **전체 오류 AUROC vs decisive AUROC**: 양성 집합만 다르다. 전체 오류 = 모든 오류 이벤트 스텝, decisive = decisive 스텝만. 음성은 둘 다 같은 clean 스텝.
- **트레이스 수준 max / mean**: 실행 하나의 점수를 스텝 점수의 최댓값 또는 평균으로 요약하고, 실행 성공 여부를 양성으로 하는 AUROC. 역할 스코프 채점률 80% 미만인 실행은 제외(커버리지 규칙).
- **귀속 정확도**: 점수 argmax 스텝이 라벨된 decisive 스텝과 정확히 같은가(exact) / 앞뒤 한 스텝 안인가(±1) / 같은 에이전트인가(agent).
- **recall@FPR10, 탐지 지연**: clean 스텝의 10%만 잘못 울리는 임계값에서 잡은 오류 비율, 그리고 decisive 이후 임계값을 처음 넘기기까지의 스텝 수.
- **백분위 임계값 vs 라벨 최적**: 라벨 없이 점수 상위 5%·10%를 자르는 규칙과, 라벨로 Youden J를 최대화한 임계값의 recall·FPR 비교.
- **매칭 부표**: D1과 D2가 모두 채점한 스텝 교집합에서만 다시 계산한 AUROC(둘 다 모든 비보조 스텝을 채점하므로 교집합 = 전체).
- **subtag**: 라벨의 서술용 태그(hallucination_like / handoff_induced / reasoning_like / none). 판정에 쓰지 않는다(§1.2).

(1)은 지금도 잡음의 주 원인이다 — 남은 오탐 14건 중 (1)만 걸린 것이 대부분이고, 지시문의 자연어를 도구 군으로 옮기는 정규식의 정밀도가 병목이다. **(2) 기록에 없는 값으로 호출**은 "지어낸 식별자로 도구를 부른" 스텝이다 — 라벨된 환각성(hallucination_like) subagent 오류 29건 중 23건이 여기 걸리고, 이 어긋남만 켰을 때 플래그의 82 %가 실제 오류다(`get_user_details(user_id='rossi_123')`: 고객은 성 'Rossi'만 말했다). 지어낸 값은 발언이 아니라 **인자**에 있었다: 처음 설계했던 발언 값 근거 검사(폐기)는 같은 49건 중 38건을 "값이 전부 근거 있음"으로 봤다. **(3′) 호출이 성립하지 않음**은 도구가 오류를 돌려준 스텝이다 — 대개 (2)의 증상이다: 기록에 없는 값으로 부른 호출이 "user not found"로 돌아오는 식이라 airline subagent에서 (3′) 57건 중 32건이 (2)와 겹친다. 그래도 (2)의 식별자 패턴이 놓친 잘못된 인자를 도구 쪽 실패로 잡아 주고, 이 어긋남만 켰을 때 플래그의 93 %가 실제 오류다. 파일 도구와 래퍼 행의 오류를 제외하는 이유는 표의 미채택 행이 보여 준다: 그것까지 넣으면 오탐이 14 → 22건으로 늘고 그중 9건이 사건 기록 파일의 첫 `read_file` 실패(설계상 정상)와 래퍼 행이었다. 세 어긋남을 합친 채택 정의는 recall 0.48 / FPR 0.07 / precision 0.62, **F1 0.54**다. 기각한 변형 하나 더: "항공편 없음"처럼 실패를 보고한 handoff를 (1)에서 면제하는 안은 오탐 8건을 없애지만 참양성 5건도 함께 지웠다 — 그중 하나가 decisive인 airline_002 스텝 19로, "실패"가 에이전트 자신의 잘못된 인자에서 나온 경우였다. 실패 문구로는 정직한 실패와 자초한 실패를 가를 수 없어 기각했고 `reported_failure`는 서술 필드로만 남긴다. 결과 처리 검사(repeat · ignored · empty · schema)는 정의에 넣지 않았다 — repeat는 정당한 재조회가 많아 FPR만 올리고(0.07 → 0.31), ignored는 아무것도 더하지 않는다(§4.2.9). planner 스텝에서는 D2가 거의 울리지 않는다(플래그 2건, recall 0.04) — planner는 도구를 직접 다루는 자리가 아니라 D2는 **subagent 층의 모듈**이다.

D2가 놓치는 airline subagent 오류 48건 중 25건은 두 부류다: tool 범주 오류 26건 중 잡지 못한 10건 — 인자의 **출처는 맞는데 선택이 틀린** 경우(다른 예약의 날짜를 쓰거나 고객이 말한 것과 다른 편을 고름)처럼 값은 기록에 있어 (2)에 걸리지 않고 호출도 성립해 (3′)에 걸리지 않으며 지시가 요구한 도구는 불렀으므로 (1)에도 걸리지 않는 것 — 과 tool 범주 밖(reasoning_stability·handoff)의 15건. 전자는 "어느 기록 값이 이 인자에 맞는가"를 판정해야 하고 후자는 발언·경계 층의 문제라, 모두 현재 D2의 질문 밖이다. decisive AUROC 0.59(양성 8)는 결정적 실패 8건 중 2건이 플래그된 결과다 — D2는 결정적 실패를 짚는 검사가 아니라 특정 종류의 실수를 정밀하게 표시하는 검사다.

D3 report→planner는 0.59 [0.47, 0.72], **D3 instruction→premise는 0.40으로 우연 아래**다: 지시문의 값이 subagent 첫 발언에 덜 보존될수록 오류일 것이라는 가설은 이 데이터에서 성립하지 않는다.

| D2 행동 근거성 | planner | 31 (25 / 6) | 0.373 [0.187, 0.540] | 0.373 [0.173, 0.540] |

성공 런이 6건뿐이라 CI가 넓다. planner D1은 트레이스 수준에서도 0.81(max)로, 실행 하나에서 가장 뜻밖이었던 planner 결정 하나의 크기가 성패를 가른다. subagent 항목은 max 요약에서 0.5 부근이다. D2는 모든 스텝을 채점하므로 커버리지 규칙에 걸리는 런이 없고, 이진 플래그의 max는 "한 번이라도 울렸나"라 0.61 [0.40, 0.82], mean(런 안의 플래그 비율)은 0.61 [0.35, 0.84]으로 방향은 맞지만 CI가 0.5를 포함한다. 트레이스 수준 지표는 이 데이터에서 항목 간 순위를 주장할 근거가 되지 못하며, planner D1의 방향 정도만 말할 수 있다. AIME에서는 같은 planner D1이 0.34로 뒤집힌다(§4.2.12).

#### 4.2.4 decisive 스텝 귀속 정확도

무엇을 재나: 점수 최댓값 스텝이 라벨 decisive 스텝과 얼마나 일치하는가. 모집단 = decisive_step이 있는 airline 실패 런 24건(역할 스코프에 채점 스텝이 있는 런만). 동점은 planner 우선 → 이른 스텝.

| 항목 | 역할 | n_runs | 정확 일치 | ±1 | 에이전트 일치 |
|---|---|---|---|---|---|
| D1 1 − p_actual | planner | 24 | 0.167 | 0.250 | 0.667 |
| D1 handoff 층 | planner | 24 | 0.208 | 0.292 | 0.667 |
| D1 1 − p_actual | subagent | 24 | 0.000 | 0.292 | 0.208 |
| D2 행동 근거성 | subagent | 24 | 0.042 | 0.292 | 0.250 |
| D2 행동 근거성 | planner | 24 | 0.125 | 0.292 | 0.667 |
| D3 report→planner | planner | 23 | 0.174 | 0.217 | 0.652 |

스텝 정확 일치는 모두 0.21 이하다. D1은 순위(AUROC)는 있으나 "가장 불안정한 스텝 = decisive 스텝"은 아니며, ±1 허용에서도 0.25–0.29다. 에이전트 일치는 planner 항목이 0.65–0.67인데, airline 결정적 실패 24건 중 16건이 planner 스텝이라 planner 스코프 항목은 역할을 맞히기 쉽다. D2는 이진 플래그라 argmax가 "가장 이른 플래그 스텝"이 되어 귀속에는 맞지 않는 형태다(subagent 정확 일치 0.04). AIME에서는 D2 subagent의 정확 일치가 0.50, 에이전트 일치가 0.86으로 예외적으로 높은데, 그 이유는 §4.2.12에서 다룬다.

#### 4.2.5 recall@FPR10과 탐지 지연

무엇을 재나: 거짓 양성률을 10 %로 묶었을 때 잡히는 오류의 비율과, 실패 런에서 그 임계값을 decisive 이후 처음 넘기는 시점. 모집단 = 스텝 AUROC와 같다(임계값은 같은 역할·도메인의 clean 스텝으로 정함).

| 항목 | 역할 | 임계값 | 달성 FPR | recall(전체 오류) | n_pos | n_crossed / n_failed | 지연 중앙값 (스텝) |
|---|---|---|---|---|---|---|---|
| D1 1 − p_actual | planner | 0.247 | 0.095 | 0.196 | 46 | 18 / 24 | 4.0 |
| D1 1 − confidence | planner | 0.333 | 0.095 | 0.174 | 46 | 16 / 24 | 5.5 |
| D1 handoff 층 | planner | 0.704 | 0.095 | 0.065 | 46 | 8 / 24 | 5.5 |
| D1 1 − p_actual | subagent | 0.294 | 0.100 | 0.146 | 48 | 12 / 24 | 3.0 |
| D3 instruction→premise | planner | 0.800 | 0.091 | 0.190 | 21 | 1 / 24 | 0.0 |

이진 항목(D2, D3 report→planner)은 FPR ≤ 10 % 조건에서 임계값이 최댓값(1.0)으로 밀려 FPR 0 · recall 0이 되므로 표에서 뺐다. D2는 자기 플래그에서 평가한다: airline subagent에서 recall 0.48 @ FPR 0.07, F1 0.54(§4.2.2), 실패 런 24건 중 17건에서 decisive 이후 플래그가 켜지고 그 지연 중앙값은 2스텝이다. FPR 10 %에서 D1 planner의 recall은 0.20이고, 실패 런 24건 중 18건에서 decisive 이후 임계값을 넘겼으며 그 시점은 decisive로부터 중앙값 4스텝 뒤다. 즉 D1은 결정적 실패 "그 스텝"보다 그 직후의 흔들림을 잡는다.

#### 4.2.6 임계값 실험: 백분위 vs 라벨 최적

<!-- TABLE: thresholds -->
무엇을 재나: 라벨 없이 정한 백분위 임계값이 라벨로 정한 최적 임계값에 비해 recall·FPR을 얼마나 잃는가. 모집단 = 백분위 풀은 airline 31런의 채점된 스텝 전체, FPR·recall은 라벨된 airline 스텝. `Δ`는 같은 셀의 라벨 최적(Youden J 최대) 행과의 차이.

| 항목 | 역할 | 규칙 | 임계값 | FPR | recall | Δ recall | Δ FPR |
|---|---|---|---|---|---|---|---|
| D1 1 − conf | planner | 상위 5 % (p95) | 0.431 | 0.027 | 0.043 | −0.870 | −0.622 |
| D1 1 − conf | planner | 상위 10 % (p90) | 0.351 | 0.074 | 0.174 | −0.739 | −0.574 |
| D1 1 − conf | planner | 라벨 최적 | 0.0074 | 0.649 | 0.913 | – | – |
| D1 1 − conf | subagent | 상위 5 % (p95) | 0.328 | 0.068 | 0.083 | −0.458 | −0.268 |
| D1 1 − conf | subagent | 상위 10 % (p90) | 0.241 | 0.105 | 0.146 | −0.396 | −0.232 |
| D1 1 − conf | subagent | 라벨 최적 | 0.0027 | 0.337 | 0.542 | – | – |
| D3 report→planner | planner | 상위 5 % = 10 % | 1.000 | 0.121 | 0.161 | −0.484 | −0.318 |
| D3 report→planner | planner | 라벨 최적 | 0.667 | 0.439 | 0.645 | – | – |

D1의 라벨 최적 임계값은 1 − confidence 기준 0.003–0.007, 즉 **confidence가 0.995 아래인 결정을 전부 플래그**하는 지점이고 그때 FPR은 0.34–0.65다. 분포의 대부분이 confidence > 0.99에 몰려 있어 "상위 5–10 %"만 잡는 백분위 규칙은 recall을 0.04–0.17로 떨어뜨린다(planner Δ recall −0.74 ~ −0.87). D1은 순위 신호(AUROC)로는 쓸 수 있지만, 낮은 FPR을 유지하는 고정 임계 알람으로는 오류의 대부분을 놓친다. D3은 값이 소수의 이산 수준에 몰려 p95와 p90이 같은 임계값에 걸린다. D2는 0/1이라 백분위 규칙과 라벨 최적이 모두 "플래그 = 1"로 같고(airline subagent: FPR 0.074, recall 0.479), 라벨 없이 운영해도 잃는 것이 없는 유일한 항목이다.

#### 4.2.8 매칭 부표

무엇을 재나: 항목 간 모집단 차이를 없앤 상태의 AUROC. 모집단 = D1과 D2가 동시에 채점한 라벨 스텝의 교집합. D2가 절차형으로 바뀌어 모든 비보조 스텝에 0/1을 주므로 교집합은 라벨 스텝 전체(1,296 결정 지점)와 같고, 매칭 부표는 §4.2.2의 본 표와 일치한다(airline subagent: D1 1 − conf 0.539 [0.439, 0.629], D2 0.703 [0.625, 0.778]). 즉 D1과 D2의 subagent 셀 차이는 모집단 차이가 아니다. (조건별 채점을 하던 이전 구성에서는 교집합이 subagent 195스텝이었고, 그때도 두 항목의 CI는 본 표와 겹쳤다.)

#### 4.2.9 D2 구성 요소 선택: 도구 로그 검사 vs `category = tool` 라벨

무엇을 재나: 도구 호출 로그에서 뽑을 수 있는 이진 검사 다섯 종 각각이 tool 범주 라벨 이벤트와 스텝 단위로 겹치는 정밀도·재현율. 이 가운데 error(호출이 오류로 돌아옴)만 파일 도구·래퍼 행을 제외한 (3′)로 D2에 들어갔고, 나머지 넷("도구 호출 결과를 잘못 다뤘나")은 로그 흐름만으로는 판정할 수 없다고 보아 넣지 않았다. 이 표는 그 선택의 배경이다. 모집단 = 라벨된 airline 비보조 스텝 826개(cascade 포함); 어떤 도구 호출이든 그 검사에 걸리면 플래그.

| 검사 | tool 라벨 양성 | 플래그 | TP | 정밀도 | 재현율 |
|---|---|---|---|---|---|
| error (미회복 오류 결과) | 82 | 83 | 45 | **0.542** | **0.549** |
| repeat (같은 호출 반복) | 82 | 78 | 17 | 0.218 | 0.207 |
| ignored (결과 미사용) | 82 | 31 | 3 | 0.097 | 0.037 |
| empty (빈 결과) | 82 | 12 | 0 | 0.000 | 0.000 |
| schema (인자 스키마 위반) | 82 | 0 | 0 | n/a | 0.000 |

검사 다섯 종 가운데 airline에서 tool 라벨과 실질적으로 겹치는 것은 **error** 하나다(정밀도 0.54 · 재현율 0.55; cascade 포함 모집단). 그 오탐의 대부분이 사건 기록 파일의 첫 `read_file` 실패와 래퍼 행이어서, 둘을 제외한 (3′)는 cascade 제외 subagent 셀에서 정밀도 0.93이 된다(§4.2.2 구성 이력) — 그래서 (3′)만 D2에 들어갔다. repeat는 airline에서 정당한 재조회가 많아 0.22에 그치고(같은 검사가 AIME에서는 0.86 — §4.2.12), D2에 더하면 FPR만 오른다(§4.2.2). schema 위반은 30런에서 한 번도 없었고 empty 12건은 모두 tool 라벨과 무관했으며, ignored는 (1)∪(2)에 아무것도 더하지 않는다. 다섯 검사는 시스템 집계의 서술 열로만 남긴다.

#### 4.2.10 subtag 서술 분석

무엇을 재나: subtag별로 어느 항목의 점수가 높았는가(서술 통계, 판정 아님 — §1.2). 모집단 = 라벨된 오류 스텝 중 그 항목이 채점한 스텝. **이 표는 두 도메인 합산**이다(`eval/subtags.md`는 도메인을 나누지 않음). `mean`은 그 subtag의 오류 스텝에서 항목 점수의 평균, `flagged`는 항목의 p90 임계값 이상인 비율이다.

| subtag | n_steps | D1 1 − conf mean / flagged | D2 플래그 비율 | D3 report→planner mean / flagged |
|---|---|---|---|---|
| hallucination_like | 69 | **0.122** / 0.159 | **0.464** | 0.800 / 0.000 (n = 1) |
| handoff_induced | 93 | 0.099 / 0.151 | 0.097 | **0.664** / 0.226 (n = 62) |
| reasoning_like | 92 | 0.019 / 0.022 | 0.185 | 0.913 / 0.500 (n = 2) |
| none | 180 | 0.061 / 0.083 | 0.289 | 0.493 / 0.000 (n = 4) |

항목마다 반응하는 subtag가 다르다. D1 불안정성은 hallucination_like·handoff_induced 스텝에서 높고(0.10–0.12) reasoning_like 스텝에서는 0.02로 거의 0이다 — 추론 오류가 나는 스텝에서 모델은 흔들리지 않는다. D2는 hallucination_like 스텝의 0.46을 플래그하고 — 그 대부분이 (2) 기록에 없는 값과 그 증상 (3′)다 — subtag 없는 tool 오류(none) 0.29, reasoning_like 0.18, handoff_induced 0.10 순이다. none의 0.29는 (3′)가 더해지며 오른 부분으로, 잘못된 인자로 부른 호출이 오류로 돌아온 스텝이다; reasoning_like의 0.18은 대개 AIME에서 검증 도구를 부르지 않은 스텝((1))이다. 즉 D2는 네 subtag 가운데 환각성 오류에 가장 선택적으로 반응한다. D3 report→planner의 missing 비율은 handoff_induced에서 0.66으로 높다. (항목별 p90 임계값으로 세는 any-flag 비율은 D2의 p90이 0으로 내려가 모든 스텝을 "플래그"로 세는 산출 결함이 있어 여기서는 보고하지 않는다.)

(AIME 집계는 §4.2.12.) 이 표는 §4.3의 라우팅 결정(어느 역할에 어느 항목을 붙일지)을 데이터로 뒷받침하는 용도이고, 판정이 아니라 검토 우선순위다.

#### 4.2.12 보조 실험: AIME 2026

무엇인가: 같은 하네스로 30회 실행·라벨·채점한 수학 도메인이다. 설계 시점에는 airline과 동격의 두 번째 도메인이었으나, 결과 검토에서 **멀티에이전트 과제로 부적합**하다고 판단해 보조 실험으로 내렸다(사용자 결정, 09-09 06:30; 부록 A.17). 이 규모에서 관찰된 이유는 세 가지다. (1) solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적다 — 라벨된 planner 오류 이벤트가 6건뿐이다(airline 100건). (2) subagent의 행동이 사실상 강제된다 — solver·verifier는 `run_python`을 부르거나 보고하는 것 외의 선택지가 없다. (3) 여러 셀이 airline과 반대 방향이다 — planner D1의 트레이스 수준 AUROC가 airline 0.81, AIME 0.34다. planner→subagent 분해가 형식적이어서 "handoff·도구 선택의 불안정"이라는 가설이 잴 대상 자체가 적다. 따라서 AIME는 역할 × 도메인 교훈의 대비 사례로만 쓴다. 모든 수치는 `eval/metrics.md`에 그대로 있다.

### 4.3 해석과 한계 (Discussion)

**작동한 것.** 주 실험 airline에서 D1의 불안정성 지표는 planner 결정에서 라벨된 오류를 구별한다(1 − p_actual 0.63, decisive 0.75; 트레이스 수준 max 0.81). planner는 매 스텝 "어느 subagent 또는 도구를 부를지"를 여러 후보 사이에서 정하는 자리라, 실패가 실제로 결정의 흔들림으로 나타나는 곳이다. 세 점수(1 − confidence, 1 − p_actual, margin) 중 1 − p_actual이 일관되게 가장 높은데, 결정적 실패의 상당수가 "분포는 뾰족한데 그 뾰족한 쪽이 아닌 행동을 실행한" 경우임을 뜻한다. subagent 층에서 부분적으로 작동한 것은 행동 근거성 D2다: "이 도구 호출은 기록이 요구하고 허용한 것인가"의 세 어긋남(기록이 요구한 호출을 하지 않음 ∪ 기록에 없는 값으로 호출 ∪ 호출이 성립하지 않음) 중 하나라도 걸리면 1을 주는 플래그가 clean 스텝 7 %의 오탐으로 airline subagent 오류의 절반(23/48, 도구 범주 오류의 62 %)을 잡는다 — precision 0.62, recall 0.48, **F1 0.54**(AUROC 0.70). 정밀한 부분은 (2)와 (3′)다 — (2)만 켜면 플래그의 82 %, (3′)만 켜면 93 %가 실제 오류이고 (3′)는 대개 (2)의 증상이다 — 이고 잡음의 대부분은 (1)의 지시문→도구 매핑에서 온다(AIME에서는 (1)과 (3′)가 주력, §4.2.12). D2는 단독 탐지기가 아니라 특정 종류의 실수를 정밀하게 표시하는 부분 검사로 읽어야 한다. 어긋남을 따로 AUROC로 매겼던 처음 평가는 이진 검사의 재현율 한계를 판별력 부족으로 잘못 읽은 것이었다(§4.1.4).

**작동하지 않은 것.** subagent 스텝에서 D1은 0.54, decisive에서는 0.36으로 우연 이하다. 가장 그럴듯한 기제는 subagent의 다음 행동이 planner의 지시문에 의해 거의 강제된다는 점이다: `db_agent`는 조회를 부르는 것이 정해져 있어 분포가 뾰족하고(confidence > 0.99가 subagent에서 더 많다), 오류는 "어느 도구를 부르는가"가 아니라 "무슨 인자로, 무슨 결론으로"에서 난다. D1이 재는 것은 후보 집합 위의 분포이므로 그 층의 오류는 원리적으로 보이지 않는다. subagent의 no_tool은 구조상 "보고하고 planner로 복귀"라(두 도메인 260/260건 다음 스텝이 planner), 문제는 끝내기로 한 결정의 흔들림이 아니라 끝내기 전에 지시받은 일을 했는가다. 이를 라벨 없이 가르는 것이 D2 조건 (1)(지시→행동 대조)이고, 지시문의 자연어를 도구 군으로 옮기는 정규식의 정밀도가 그 병목이라 다음 단계는 그 매핑을 도구 스키마 설명에서 자동으로 만드는 것이다. D2가 놓치는 것은 인자의 출처는 맞고 호출도 성립했는데 선택이 틀린 tool 오류(26건 중 10건)와 값은 맞는데 결론이 틀린 추론 오류다. 발언 층을 위해 처음 설계한 문자열 대조 검사("발언의 값이 기록에 있는가")는 0.47로 신호가 없었다 — 지어낸 값은 발언이 아니라 인자에 있었고(환각성 오류 49건 중 38건), 값이 다 있어도 결론이 틀린 오류는 원리적으로 보이지 않기 때문이다. 그 자리를 위해 설계한 D4(근거 vs 응답의 관계를 LLM이 판정)는 8B 파일럿에서 판정 신뢰도가 부족해 결과에 쓰지 않았다(한계). **그 결과 "값은 맞는데 결론이 틀린" 추론 오류 층(airline 라벨의 reasoning_like 30건, 두 도메인 합산 92건)은 이 연구의 어느 검사도 담당하지 않는다.** 이것이 남은 가장 큰 미해결 항목이다. D3 instruction→premise는 0.40으로 가설과 반대다: subagent가 첫 발언에서 지시문의 값을 되풀이하지 않는 것은 정상 handoff에서도 흔하고(평균 fidelity 0.74), AUROC의 부호는 반대 경향(문제가 있는 handoff에서 오히려 더 되짚음)을 시사하지만 이 데이터로 확인한 것은 아니다. 이 방향은 신호가 아니라 서술 통계로만 남긴다.

**임계값의 실용성.** D1은 순위 지표로는 쓸 수 있지만 고정 임계 알람으로는 약하다. 라벨 최적 임계값은 confidence 0.995 부근, 즉 "조금이라도 흔들린 결정은 전부"이고 그때 FPR은 0.34–0.65다. 분포의 대부분이 confidence > 0.99에 몰린 상태에서 상위 5–10 % 백분위 규칙은 recall을 0.04–0.17로 떨어뜨린다. 운영에서 D1은 트레이스를 검토 우선순위로 정렬하거나 다른 항목과 교차할 때 쓰고, 단독 알람 임계값은 두지 않는 편이 맞다. 탐지 지연(중앙값 4스텝)과 회복 궤적(오류 다음 스텝에 정점)은 같은 이야기를 한다: D1이 잡는 것은 결정적 실패 그 스텝이 아니라 그 직후 planner가 상황을 수습하려 할 때의 흔들림이다. 반대로 D2는 0/1 플래그라 임계값이 없고 라벨 없이 운영해도 잃는 것이 없다(airline subagent FPR 0.07, recall 0.48, F1 0.54); (2)∪(3′)만 켠 고정밀 구성(FPR 0.02, precision 0.84, recall 0.33)도 알람으로 바로 쓸 수 있다.

**측정 잡음이 뜻하는 것.** 같은 요청도 KV-cache 상태에 따라 logp가 약 0.002, confidence가 약 0.005 흔들린다(§4.1.5). 이 크기 아래의 차이는 신호가 아니다. 라벨 최적 임계값(1 − confidence 0.003–0.007)이 바로 이 잡음 수준에 있다는 점은, 그 임계값이 실제로는 "confidence가 정확히 1이 아닌 결정"을 고르는 규칙이며 재현 가능한 경계가 아님을 뜻한다. D1의 유효 자릿수는 소수 둘째 자리까지이고, 항목 간 AUROC 차이도 부트스트랩 CI가 겹치면 순위를 주장하지 않는다.

**감사 MAS 설계에 대한 교훈.** 가장 큰 결과는 항목의 성능이 항목 자체보다 **역할 × 도메인**에 의해 갈린다는 점이다. 역할 축은 주 실험 안에서 보인다: 같은 D1이 planner에서 0.63–0.75, subagent에서 0.5 아래이고, 반대로 D2는 subagent에서 0.70(F1 0.54), planner에서 0.52(플래그 2건)다. 도메인 축은 보조 실험이 보여 준다: 같은 planner D1이 트레이스 수준에서 airline 0.81, AIME 0.34로 뒤집히고, 같은 반복 호출 로그 검사가 AIME 정밀도 0.86, airline 0.22다(§4.2.12). 감사 파이프라인은 "모든 스텝에 모든 항목"이 아니라 역할과 도메인에 항목을 배정하는 라우팅으로 짜야 한다: planner 결정에는 D1, subagent의 도구 층에는 행동 근거성 D2((1)의 도구 군 매핑은 도메인별로 만듦)를 두고, D3은 handoff 경계의 서술 프로파일로만 쓴다. 발언의 결론 층은 비어 있다(D4 설계만). §4.2.11의 시스템 단위 집계가 그 라우팅 결과를 에이전트·엣지 단위로 보여 주는 출력이다. 라벨 30런(airline)으로는 셀당 표본이 작아 이 배정의 세부는 잠정적이며, 항목 간 결합(교차 플래그)은 라벨을 늘린 뒤에 평가해야 한다.

#### 한계 (Limitations)

- **라벨러가 사람이 아니다.** 어노테이터는 Claude 서브에이전트이고, 품질 관리도 같은 모델 계열의 다른 인스턴스가 했다. 스팟체크의 decisive 일치 6/6은 높지만 이벤트 집합 Jaccard 0.563은 "무엇을 오류로 셀 것인가"의 자유도가 크다는 뜻이며, RUBRIC §5b는 그 자유도를 recall 쪽으로 고정한 **규약**일 뿐 정답이 아니다. 모델-모델 일치도는 사람-모델 일치도의 상한도 하한도 아니다. 라벨러는 `summary.md`만 읽으므로 요약이 흘린 것은 라벨에도 없다.
- **주 실험은 30회 규모다.** 본문 수치는 airline 30회(성공 6 / 실패 24)에서 나왔다. 항목 × 역할로 쪼개면 셀당 유효 표본이 작고(decisive 양성 planner 16, subagent 8) 부트스트랩 CI가 넓다. 항목 간 순위를 CI 겹침 없이 주장할 근거로는 부족하며, 성공 6건 때문에 트레이스 단위 지표는 특히 불안정하다.
- **주 근거가 도메인 하나다.** 결론의 근거는 τ-bench airline(정책·DB 조회) 하나이고, 두 번째 도메인으로 실행한 AIME 2026은 멀티에이전트 과제로 부적합해 보조 실험으로 내렸다(§4.2.12). 검색·코딩·장기 실행 워크플로는 다루지 않았다. 따라서 "역할 배정이 성능을 가른다"는 교훈은 한 도메인 안의 관찰이고, 도메인 축의 대비(§4.2.12)는 부적합한 도메인과의 대비라 일반화 근거로는 약하다. 두 도메인의 실패 양상(정책 위반 vs 빈 stdout 위조·반복 루프)이 서로 달라 도메인 평균(합산 셀)은 해석 가치가 낮다.
- **단일 실행 모델과 로깅 계약 전제.** 실행·시뮬레이터·채점이 모두 Qwen3-32B 한 계열이다. 다른 모델 계열에서 D1 분포가 같은 모양일 보장이 없다. 전제 조건은 **완전 관측 로깅 계약** — 도구 결과, 모든 메시지, 모델이 실제로 본 입력, 그리고 실행 모델의 logprob 접근이다. 출력만 남는 로그에서는 D1·D2·D3이 아예 동작하지 않으므로, 이 결과의 프로덕션 **일반화**는 불가하다.
- **bf16 로짓 양자화.** D1 확률은 채점 서버의 bf16 계산 결과이며, 실행 서버나 prefill 경로로 계산하면 반올림이 달라 logp가 0.1 안팎, confidence가 0.005 안팎 흔들린다. 어느 계산도 다른 계산의 기준이 아니므로 이 크기를 측정 잡음으로 두고 임계값 민감도를 함께 보고한다. 절대 logp 값을 신호로 쓰는 확장(예: perplexity 임계)은 정당화되지 않는다.
- **D1이 덮는 범위는 유한한 다음 행동 결정뿐이다.** 도구·subagent 선택처럼 후보 집합이 닫힌 지점에만 쓰고, 텍스트 환각에는 쓰지 않는다(과신 환각에 취약하므로 — §2). 도구 호출 인자 속 값의 신뢰도는 D2 어긋남 (2)의 기록 대조가 담당하지만, 발언 속 값과 결론 자체의 옳고 그름은 이 연구에서 담당 검사가 없다.
- **D1 커버리지가 100%가 아니다.** 채점 서버의 24576 토큰을 넘는 prefix(`prefix_too_long`), 경계 단언 실패, 시간 컷으로 미채점 결정 지점이 남고 `d1_unscored.json`에 유형별로 집계된다. 트레이스 단위 지표는 역할 스코프 채점률 80% 미만인 런을 아예 제외하므로, 커버리지 손실은 모집단 축소로도 나타난다.
- **추출기(8B) 오류가 하류로 전파된다.** D3은 Qwen3-8B가 handoff 양쪽 발언을 atomic fact로 구조화한 결과 위에서 판정한다(D1·D2는 LLM을 쓰지 않는다). 추출 실패는 D3의 오탐/미탐으로 그대로 넘어가며, **추출기 민감도 실험(다른 크기·다른 프롬프트로 재추출)은 실행하지 않았다.**
- **τ-bench 사용자 시뮬레이터를 대체했다.** 원본의 litellm 경로 대신 같은 모델을 쓰는 raw httpx **시뮬레이터**(`src/data/tau_user.py`)로 바꿔 요청 본문 캡처와 thinking off / temperature 0을 보장했다. 시스템 프롬프트와 인터페이스는 같지만 원본과의 동등성은 약해졌고, τ-bench 공개 성공률과 직접 비교할 수 없다.
- **환각 도구 이름을 사후에 후보 집합에 넣는다.** 모델이 바인딩되지 않은 이름을 호출하면 그 이름을 A에 추가해야 실제 행동의 확률이 정의된다. 이는 감사 시점에만 가능한 조작이며, 실시간 가드레일에서는 후보 집합을 사전에 닫을 수 없다.
- **D3 방향 2는 주입 프롬프트 준수도에 의존한다.** subagent가 첫 발언에서 전제를 3–5개로 선언하도록 시스템 프롬프트로 강제했지만, 모델이 그 지시를 지키지 않으면 비교 집합이 비고 방향 2는 NA가 된다. 준수율이 낮으면 방향 1(보고→인용)만 보고한다.
- **`files` 삭제가 전파되지 않고 todo는 공유되지 않는다.** 공유 파일시스템은 delta reducer 기반이라 subagent의 파일 **삭제**는 planner state로 병합되지 않는다(`docs/notes/deepagents_probe.md`). `todos`는 deepagents의 state 규약상 양방향 제외다. 두 경로 위의 실패는 이 기록에 남지 않는다.
- **순차 위임 그래프만 검증했다.** planner → subagent의 **순차** orchestrator-worker 한 형태이며, 병렬 fan-out, 에이전트 간 직접 통신, 순환 그래프, 다중 planner는 실행하지도 감사하지도 않았다.
- **D4(근거 의존 LLM 판정)는 설계만 있고 결과에 쓰지 않았다.** 발언 층을 위해 §3.3의 D4를 Qwen3-8B 판정기로 subagent 응답 스텝 467개에 파일럿했으나 채택하지 않았다: airline subagent AUROC 0.47 [0.38, 0.57], 플래그 스텝의 정밀도 17 %, clean 스텝의 39 %를 플래그(clean 평균 점수 0.13 vs hallucination_like 0.11); AIME는 정밀도 75 % / 재현율 21 %. 근거 텍스트 길이가 원인은 아니다(스텝당 근거 중앙값 744자, p90 3,560자; 입력 상한 12,000자) — 8B 판정기는 짧은 근거도 잘못 읽는다. 더 큰 판정 모델(32B)은 시도하지 않았다. 따라서 "코드 판정 vs LLM 판정"의 비교는 이 파일럿 한 점뿐이며, 발언 층의 공백은 판정 모델 크기의 문제인지 설계의 문제인지 이 연구로는 가르지 못한다(부록 A.20).
- **선택 모듈은 미구현이다.** D8(축약 손실), D10(계획-행동 일치), D6(재도출)은 §3.3에 설계만 있고 **미구현**이다.

### 4.4 기대 효과 (Expected Impact)

Align류 운영 솔루션(성공·실패가 섞인 대량의 에이전트 로그를 사후에 보는 제품)에 그대로 얹히는 것을 목표로 설계했다.

**1. 라벨 없는 순위 + 근거 포인터 → 사람 검수 루프.** 탐지기는 정답·reward·라벨을 입력으로 받지 않는다. 운영 로그에 그대로 돌리면 스텝마다 항목별 신호와 근거 포인터(어느 스텝의 어느 도구 결과·어느 보고와 어긋났는지)가 나오고, 검수자는 트레이스를 처음부터 읽는 대신 상위 몇 %의 스텝만 열어 확인한다. 확인 결과는 다시 임계값과 rubric으로 돌아간다 — 순위 → 소량 검수 → 임계값 갱신의 닫힌 루프이며, 각 회차의 비용이 검수한 스텝 수에 비례한다.

**2. 트레이스가 아니라 에이전트 시스템을 평가한다.** 시스템 집계 보고서는 에이전트(역할)별로 결정 수·저신뢰 결정 비율·D2 플래그 비율(조건별)·도구 로그 검사 비율을, handoff 엣지별로 건수·충실도 평균·저충실도 비율·누락/왜곡 상위 키를 낸다. "이 시스템은 어디가 약한가"에 대한 답이 트레이스 목록이 아니라 **역할과 엣지 위의 프로파일**로 나오므로, 프롬프트 수정·도구 스키마 변경·subagent 분리 같은 조치의 대상이 바로 지목된다. 개별 트레이스에 통합 점수를 붙이지 않는 것도 같은 이유다 — 통합 점수는 조치로 번역되지 않는다.

**3. 로깅 계약을 제품 요구사항으로 승격시킨다.** 이 파이프라인이 돌기 위해 고객 시스템이 남겨야 하는 것은 명확하다: (a) 스텝(LLM 호출)마다 **모델이 실제로 본 입력 전체** — 렌더된 메시지와 도구 스키마, (b) 응답 본문 — content, tool_calls, finish_reason, (c) 도구 호출의 인자와 **결과 원문**, (d) 공유 상태(파일·todo)의 스텝별 스냅샷과 요약 직전 원문, (e) 호출을 낸 에이전트 식별자, (f) D1을 쓰려면 실행 모델의 logprob 접근(자체 호스팅이거나 logprobs를 주는 API). (a)–(e)만으로 D2·D3이 돌고, (f)가 더해질 때 D1이 켜진다. 이 목록은 곧 온보딩 체크리스트이자 SDK 계측의 사양이다.

**4. 라벨 0에서 시작할 수 있다.** 임계값은 항목별 자기 분포의 백분위(상위 5/10%)로 정한다. 새 고객·새 도메인에 라벨이 한 건도 없어도 첫날부터 순위가 나오고, 검수가 쌓이면 그 셀에서만 라벨 최적 임계값으로 옮겨가면 된다. §4.2의 백분위 vs 라벨 최적 비교가 이 부트스트랩에서 얼마를 잃는지를 재는 실험이다.

**5. 판정 주체가 코드라 감사 가능하다.** LLM은 handoff 경계의 발언을 구조로 바꾸는 추출기(D3)로만 쓰고, 옳고 그름은 기록 검색·집합 비교가 결정한다. 판정 규칙이 코드라서 재현되고, 고객이 이의를 제기하면 근거 포인터를 그대로 보여줄 수 있으며, 규칙 변경의 영향 범위를 재실행으로 확인할 수 있다. LLM-judge 기반 제품이 겪는 "판정이 바뀌었는데 왜 바뀌었는지 모른다"는 문제가 구조적으로 발생하지 않는다.

## 부록 A. 스펙 이탈·정정 각주

계획 §9의 12건과 실험 중 추가된 항목. 형식: **스펙 → 실행 → 이유**.

1. **채점 호출의 `max_tokens=0` → `max_tokens=1`.** vLLM은 `echo=true`가 아닌 `/v1/completions`에서 `max_tokens=0`을 받지 않는다.
2. **추출기 = 실행 모델(32B) → 별도 Qwen3-8B 서버(:18002).** judge 베이스라인은 8B thinking on, D1은 실행 모델 전용 채점 서버(:18003, TP=1)에서 계측한다. 추출은 32B를 쓸 이유가 없고 실행 서버와 자원이 경합한다. AC-16의 "추출기도 같은 모델" 문구는 이로써 무효.
3. **"직접 답변" 후보 제거(스펙 v2.1–2.2) → `no_tool` = 1 − P(`<tool_call>`)로 복원.** 도구를 부르지 않는 스텝도 결정 지점이므로 후보 집합이 닫혀 있어야 분포가 정의된다.
4. **AC-20(수식 정합성 검사) 신설.** AIME 도메인에서 기록 대조 항목이 발언 값 대조 하나뿐이면 추론 오류를 잡을 수단이 없다고 보아, 발언의 수식을 sympy로 평가하는 AIME 전용 검사를 추가했다(후에 삭제, 항목 18).
5. **수식 정합성 검사를 OPTIONAL → MUST 승격.** 위와 같은 이유. AIME 절반의 트레이스가 채점 대상에서 빠지는 것을 막으려 했다.
6. **deepagents 내장 `task` 호출 → 이름 있는 래퍼 도구 호출(옵션 A′).** `task`는 대상 subagent를 인자(`subagent_type`)에 숨겨 D1이 handoff 결정을 잴 수 없다. 래퍼는 `task`의 state 규약(copy-in / merge-out)을 복제하며, `todos`는 그 규약상 비공유로 남는다.
7. **AC-11 "60건 전부" → 배치·컷 시점에 따른 n을 명시.** 시간 게이트가 배치 2를 포기시킬 수 있는 설계였기 때문이다(결과적으로 60건 전부 실행·라벨되었다).
8. **AC-10 "14:00 단일 컷" → 단계별 컷(계획 §8 타임라인) + 14:00 신규 코드 컷.** 단일 컷은 "무엇이 부분 완료인지"를 구분하지 못한다.
9. **AC-5 "결정 지점마다 분포" → 채점 완료 지점 + `d1_unscored.json` 유형별 카운트.** prefix 길이·경계 단언·시간 컷으로 미채점 지점이 남을 수 있다. 아울러 `user_sim`·`summarizer` 스텝은 결정 지점에서 제외하고, AC-4의 기록 항목에 도구 스키마·요약 직전 원문·시뮬레이터 호출·`finish_reason`을 명시했다.
10. **"분포 계산은 prefill 경로(`prompt_logprobs`)만" → decode 경로 teacher-forced 채점(`allowed_token_ids`) 단일 방법; 실행 기록 logprob은 렌더 정합 검사에만 사용.** 처음에는 prefill 경로를 정의로 두고 decode 경로를 동일성 게이트로 검증하려 했으나, prefill 경로도 기록과 같은 크기로 어긋나 게이트 자체가 기준이 될 수 없었다(§4.1.5).
11. **"τ-bench는 litellm + `OPENAI_API_BASE`" → raw httpx 사용자 시뮬레이터(`src/data/tau_user.py`).** litellm 경로로는 요청 본문·헤더 캡처와 thinking off / temperature 0 고정이 보장되지 않는다. 시스템 프롬프트와 `reset/step` 인터페이스는 원본을 따른다.
12. **출력 포맷 추가: 트레이스별 감사 보고서(P4b) + 시스템 단위 집계(P4c).** 사용자 결정(02:35). 통합 점수 대신 근거 포인터와 역할·엣지 단위 프로파일을 낸다.
13. **발언 값 대조 검사·D3 정의 보정 (라벨 컷 이후, 05:02).** 초기의 발언 값 대조 검사(발언 속 값이 기록에 있는가; 후에 폐기, 항목 18)는 근거 풀이 도구 결과와 고객 발화만이어서 AIME 문제 문장의 값과 planner 지시문의 값을 "근거 없음"으로 세었다. 모델이 그 요청에서 입력으로 받은 것(system·user·tool 메시지; 자기 이전 발화 제외)을 근거로 인정하도록 고쳤다(평균 s 0.817 → 0.847, 48/793 스텝 변경). D3(handoff 충실도)은 8B 추출기가 "Submitted 277." 같은 짧은 텍스트에서 값을 못 뽑아 fidelity 0이 되던 것을, 원문에 값이 문자 그대로 있으면 보존으로 치도록 고쳤다(report→planner fidelity 0 건수 69 → 52). 라벨은 탐지기를 보지 않고 달았으므로 정의 보정이지 라벨 맞춤이 아니며, 보정 전 출력은 `audit/_removed/`에 남겼다.
14. **D2 어긋남 (1)(기록이 요구한 호출을 하지 않음) 사후 추가 (09-09 06:00).** 결과 검토 중 subagent의 no_tool이 구조상 "보고·복귀"임을 확인하고(260/260건 다음 스텝이 planner), 끝내기 전에 지시받은 작업을 수행했는지를 보는 결정적 조건을 추가했다(`src/audit/d2_instruction.py`). 라벨을 보고 난 뒤의 추가이지만 조건은 지시문 정규식 → 도구 군 매핑만 쓰고 라벨·정답을 입력으로 받지 않는다. 다른 항목의 수치는 변하지 않았다(`eval/metrics.md` 재생성).
15. **"근거 의존도"의 귀착.** 설계 인터뷰(스펙 Round 27–28)에서 제기된 "근거 의존도"는 처음에 "subagent가 도구 결과 없이 얼마나 근거 없는 주장을 하는가 = |1 − s|"라는 발언 값 대조 검사로 확정됐다. 같은 이름으로 논의된 반사실적 버전(근거 제거 시 결론 확률의 변화, Round 22 "의존도 × p(action)")은 "logprob으로 환각·추론을 판정하지 않는다"는 원칙에 따라 보조 피처로 보류됐고 미구현이다. 발언 값 대조 검사는 결과가 없어 폐기됐고(항목 18), 발언 층은 LLM 판정형 D4(설계만, 항목 20)로 재정의됐다.
16. **인자 근거 검사(현재 D2 어긋남 (2)) 사후 추가 (09-09 06:15).** 결과 검토에서 발언 값 대조 검사가 환각성 라벨을 놓친 원인이 "값의 위치"(발언이 아닌 도구 호출 인자)임을 확인하고 추가했다. 처음에는 발언 층 검사의 두 번째 규칙으로 만들었으나 도구 호출 층의 검사이므로 D2로 합쳤다(항목 18; `src/audit/d2_args.py`, `audit/d2_args.jsonl`). 정규식과 문자열 대조만 쓰며 라벨·정답을 입력으로 받지 않는다. 공항 코드는 τ-bench `list_all_airports`의 도시명, 날짜는 자연어 표기를 근거로 인정한다. 다른 항목의 수치는 변하지 않았다.
17. **AIME를 보조 실험으로 격하 (09-09 06:30, 사용자 결정).** 계획은 두 도메인을 동격으로 두었으나(P3·AC-11), 결과 검토에서 AIME가 멀티에이전트 과제로 부적합함이 드러났다: solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적어(라벨된 planner 오류 6건) planner→subagent 분해가 형식적이고, 여러 셀이 airline과 반대 방향이다(planner D1 트레이스 max 0.34 vs 0.81). 본문(§0, §4.2 핵심 결과, §4.2.1–4.2.9, §4.3)은 airline만 보고하고, AIME 결과와 두 도메인 합산 셀은 §4.2.12에 참고로 둔다. 실행·라벨·채점은 그대로이고 모든 수치는 `eval/metrics.md`에 있다.
18. **발언 값 대조 검사와 수식 정합성 검사 삭제, 인자 근거 검사를 D2로 합침 (09-09 06:25, 사용자 결정).** (1) 발언 값 대조 검사(발언 값의 기록 근거)는 D2의 발언 규칙(숫자 주장 → 도구 근거)과 대상·판정이 겹치고 신호가 없어(airline subagent 0.47) 삭제했다. (2) 수식 정합성 검사는 AIME 전용이고 수식의 77 %가 판정불가라 삭제했다 — 이로써 수학 수식 모듈은 이 연구에 없다. (3) 인자 근거 검사는 결과가 있어(0.68, 정밀도 80 %) 유지하되 도구 호출 층의 검사이므로 D2의 조건으로 옮겼다 — 코드 `src/audit/d2_args.py`, 출력 `audit/d2_args.jsonl`; 수치는 이관 전과 같다. 삭제된 검사의 출력과 평가 이력은 `audit/_removed/`와 git 이력에 있다. 이로써 "값은 맞는데 결론이 틀린" 추론 오류 층은 이 연구에 탐지기가 없음을 §1.2·§4.3·한계에 명시했다.
19. **D2를 절차형 단일 모듈 "행동 근거성"으로 재정의 (09-09 07:00–08:05, 사용자 결정 + 매핑 버그 수정).** 결과 검토 중 D2의 세 규칙을 각각 AUROC로 매긴 것이 잘못된 평가였음이 지적됐다: 이진 검사의 AUROC는 (recall + 1 − FPR)/2로 결정되어, 정밀도 82 %·FPR 2 %인 인자 근거 검사조차 재현율 때문에 0.6대에 갇힌다. D2를 "이 행동(도구 호출)은 기록이 요구하고 허용한 것인가" 하나의 질문으로 되돌리고, 그 세 어긋남의 OR로 0/1 플래그를 내며 플래그 지표(precision·recall·F1·FPR)로 평가한다(`src/audit/d2_action.py`, 평가 항목 `D2` 하나). 정의는 세 단계로 확정됐다. **(a) 매핑 버그 수정(07:40).** (1)∪(2)의 첫 규칙 집합은 airline subagent에서 recall 0.48 / FPR 0.12 / AUROC 0.68이었으나, 오탐 23건을 라벨과 대조하자 21건이 어긋남 (1)의 한 정규식 오류였다 — 지시문의 "예약의 항공편 상세"를 항공편 검색 요구로 읽어 `get_reservation_details`로 충족한 handoff를 미충족으로 셌고, 참양성 6건도 같은 오류로 잘못된 이유에서 걸려 있었다. 검색 군은 검색 의도에만 걸리도록 고쳤다(AIME 규칙은 그대로). 수정 후 (1)∪(2)는 0.33 / 0.07 / 0.55 / AUROC 0.63. 이 수정은 **라벨을 보고 난 뒤 이루어진 매핑 버그 수정**이며 임계값 조정이 아니지만, 라벨 정보가 규칙에 들어간 사실은 그대로 밝힌다. **(b) (3′) 채택(07:55).** 도구 호출이 오류로 돌아온 스텝을 세 번째 어긋남으로 더하되, 파일 도구의 첫 `read_file` 실패(설계상 정상)와 래퍼 행(subagent 스텝에서 판정)을 제외한다 — 제외하지 않으면 오탐 14 → 22건이 되고 그중 9건이 그 둘이었다. 사용자는 (2)만, (2)∪(3′), (1)∪(2)∪(3′), 파일·래퍼 포함 변형의 수치를 보고 (1)∪(2)∪(3′)를 택했다: recall 0.48 / FPR 0.07 / precision 0.62 / F1 0.54 / AUROC 0.703 [0.625, 0.778]. (3′)는 대개 (2)의 증상(airline subagent 57건 중 32건 겹침)이지만 (2)의 식별자 패턴이 놓친 잘못된 인자를 잡는다. **(c) 기각한 변형.** 실패를 보고한 handoff("항공편 없음")를 (1)에서 면제하는 안 — 0.25 / 0.03 / 0.71(AUROC 0.61)로 오탐 8건을 없애지만 참양성 5건(decisive airline_002/19 포함, 실패가 에이전트 자신의 잘못된 인자에서 난 경우)을 함께 지워 기각했고, `reported_failure`는 서술 필드로만 남긴다. 작성 보조는 07:10에 오류 반환 조건을 사용자 확인 없이 정의에 넣었다가 지적을 받고 되돌린 뒤, 변형 수치를 제시하고 사용자가 (3′)를 택하는 순서로 확정했다. **D2에서 뺀 것**: 발언의 숫자 주장에 도구 근거를 요구하던 옛 발언 규칙(발언 층의 문제이고 정당한 무도구 보고를 오탐; `src/audit/d2_toolcalls.py`에 서술용으로 남음), empty·schema·repeat·ignored 로그 검사(서술용으로만 시스템 집계에 남김; repeat는 FPR만 0.07 → 0.31로 올림). 다른 항목의 수치는 변하지 않았다.
20. **D4는 설계만 남기고 결과에서 제외 (09-09 06:55–07:05, 사용자 결정).** 06:25에 삭제한 문자열 대조형 발언 검사와 별개로, 사용자가 처음부터 뜻한 발언 층 검사는 "근거(도구 결과 + 지시) 텍스트와 응답 텍스트를 LLM에 주고 주장별 관계(supported / derived / unsupported / contradicted)를 구조화해 받는" LLM 판정형이다. 이를 §3.3에 D4 설계로 두었다. Qwen3-8B로 subagent 응답 스텝 467개(전 실행)에 파일럿한 결과 airline AUROC 0.47, 플래그 정밀도 17 %, clean 플래그율 39 %, AIME 정밀도 75 % / 재현율 21 %로 채택 불가였다. 근거 길이는 원인이 아니고(중앙값 744자) 판정 모델의 한계로 보이나 32B 재시도는 하지 않았다. "개념만 남기고 안 쓰는 것"으로 확정: 출력은 `audit/_removed/d4_judge_8b_pilot.jsonl`, 코드는 `src/audit/unused/d4_judge.py`. §4.2에는 D4 수치를 결과로 싣지 않는다.
21. **이진 모듈 평가에 F1 추가 (09-09 08:05, 사용자 제안).** D2처럼 0/1 플래그를 내는 항목은 recall·FPR·precision에 **F1**(정밀도·재현율의 조화평균)을 더해 `eval/metrics.md` §1b "Flag-level metrics for binary items"로 보고한다(`src/eval/metrics.py`). 연속 점수 항목(D1·D3)은 그대로 AUROC가 주 지표다. D2 airline subagent F1 0.541, AIME 0.571.

## 부록 B. 재현

환경: 서버는 conda `math_infer`(vLLM 0.9.2), 나머지는 conda `agentbench`(Python 3.11, `requirements.txt`). **GPU는 1–4번만** 사용하며 포트는 18001–18003이다. 전체 절차는 README의 "Reproduce" 블록과 같다.

```bash
# 0. 설치 (agentbench 환경)
pip install -r requirements.txt
# 1. 서버 3대 (GPU 1-4)
bash scripts/serve_qwen32b.sh & bash scripts/serve_qwen8b.sh & bash scripts/serve_qwen32b_score.sh &
export OPENAI_BASE_URL=http://localhost:18001/v1 OPENAI_API_BASE=$OPENAI_BASE_URL OPENAI_API_KEY=dummy
python scripts/check_server.py && python scripts/probe_deepagents.py      # P1 / P1b 게이트
# 2. 데이터 + 실행
python -m src.data.tau --write && python -m src.data.aime --write
python -m src.run --domain airline --task 0 && python -m src.harness.validate runs/airline_000   # 스모크
python -m src.run --batch 1 --parallel 4 --resume      # 이후 --batch 2
# 3. 감사
python -m src.audit.d1 --check && python -m src.audit.d1 --all
python -m src.audit.d2_toolcalls && python -m src.audit.d2_instruction && python -m src.audit.d2_args && python -m src.audit.d2_action && python -m src.audit.d3_handoff --stats
python -m src.audit.report && python -m src.audit.system_report
# 4. 라벨 + 평가
python -m src.eval.index && python -m src.eval.summarize   # 이후 labels/RUBRIC.md에 따라 labels/<run_id>.json 작성
python -m src.eval.labels --validate
python -m src.eval.metrics && python -m src.eval.thresholds && python -m src.eval.recovery
```

원본 트레이스(`runs/<id>/steps.jsonl`, `tool_calls.sqlite`, `fs/`)는 크기 때문에 커밋하지 않는다. `runs/index.csv`, `runs/<id>/summary.md`, `audit/`, `labels/`, `eval/`, 스크립트 전체는 커밋되어 있으므로 이 문서의 모든 표는 커밋된 산출물에서, 원본 트레이스는 위 스크립트에서 재생성된다.

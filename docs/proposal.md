# 안정성 기반 멀티에이전트 실패 탐지: 실행 모델의 logprob과 기록 대조로 handoff·도구·추론 실패를 사후 감사하는 파이프라인

> 콕스웨이브 AI 리서치 및 제품화 엔지니어 직무과제 제출 문서 (2026-09-09)
> 코드: https://github.com/kangmc1/project-agent · 발표 슬라이드: `docs/slides.html`

## 0. 한 문장 요약

멀티에이전트 실패는 **불안정성**으로 드러난다. 순차 오케스트레이션에서 "다음 행동"은 유한 집합이므로 실행 모델의 실제 logprob으로 그 분포를 샘플링 없이 직접 계산하면 handoff·도구 선택의 불안정을 재고, 환각과 추론 오류는 "결론의 안정성" 하나로 묶어 **기록 대조**(출처·충실도·재도출)로 검사한다. 탐지기는 정답도 라벨도 쓰지 않는 **오프라인 감사 멀티에이전트**이며, 성공·실패 트레이스를 함께 실행한 실험으로 오탐율과 회복 여부까지 측정한다. 주 실험인 τ-bench airline 30회에서 이 가설은 **planner 결정에서 성립**했고(decisive 스텝 AUROC 0.75 [0.61, 0.86], 전체 오류 0.63 [0.54, 0.71], 트레이스 수준 max 0.81) subagent에서는 성립하지 않았으며(그 층은 도구 호출 인자의 근거 검사 0.68과 필요 도구 검사가 맡는다), 탐지기 성능은 항목보다 **역할 배정**에 의해 갈렸다(§4.2 핵심 결과). AIME 2026 30회는 보조 실험이다 — 수학 풀이는 subagent 하나가 거의 전부를 하는 구조라 멀티에이전트 과제로 부적합함이 이 규모에서 관찰됐다(§4.2.12).

## 1. 배경 (Background)

### 1.1 연구 세부 주제

- 대상: planner(오케스트레이터)가 task-specific subagent에게 일을 넘기는 **순차 멀티에이전트 시스템**(LangChain Deep Agents 하네스로 구성) — 2026년 프로덕션의 기본형인 orchestrator-worker 구조.
- 상황: **오프라인 사후 감사**. 운영 중 쌓인 실행 기록(모델이 실제로 본 입력, 출력, 도구 호출/결과, 공유 파일)을 나중에 훑어 실패를 탐지·위치 귀속하는 파이프라인. 실시간 개입(가드레일)은 범위 밖.
- 질문: 정답(ground truth)도 사람 라벨도 없는 운영 환경에서, **기록만으로** 어느 스텝에서 어떤 종류의 실패가 났는지 짚어낼 수 있는가? 그 판단의 근거를 사람이 검수할 수 있는 형태로 낼 수 있는가?

### 1.2 현재 에이전트 시스템의 문제 정의

미션이 나열한 네 유형을 이 시스템의 어디에서 관찰할 수 있는지로 다시 정의한다.

| 미션 유형 | 이 제안의 범주 | 어디서 관찰되나 | 이 제안의 검사 |
|---|---|---|---|
| handoff 문제 | **handoff 불안정** | planner가 어느 subagent를 부를지 결정하는 지점; 지시→전제, 보고→인용 경계 | D1(handoff 층) + D7 |
| 도구 사용 실패 | **도구 불안정** | 각 에이전트가 어느 도구를 부를지 결정하는 지점; 도구 호출/결과 로그 | D1(도구 층) + D3 |
| 환각 | **추론 안정성** (통합) | 도구 호출 인자와 발언의 값이 에이전트에게 주어진 기록에 있는가 | D3 규칙 3(인자 근거) + D3 규칙 1(claim→필요 도구) |
| 추론 오류 | **추론 안정성** (통합) | 결론이 근거로부터 재도출되는가 | D7(경계 왜곡)만. **값은 맞는데 결론이 틀린 추론 오류 층은 이 연구에 탐지기가 없다**(§4.3) |

환각과 추론 오류를 하나로 묶은 이유: (1) 스텝 시점에서 "지어낸 값"과 "잘못 계산한 값"은 구분되지 않는 경우가 많고 사람 어노테이터의 일치도도 낮다(MAST, Who&When의 세부 유형 κ), (2) 운영상 중요한 것은 "이 결론을 믿어도 되는가"이며 원인 분류는 사후 태그로 충분하다, (3) 두 유형 모두 "근거로 지지되지 않는 결론이 궤적에 유입된다"는 하나의 사건이다.

### 1.3 차별점 (Novelty)

1. **실행 모델의 실제 logprob으로 유한 행동 집합 위의 분포를 계산한다.** 공개 트레이스 벤치마크(Who&When, TraceElephant)는 GPT-4o 출력만 남아 프록시 모델로 재생해야 하지만, 우리는 실행과 채점에 같은 가중치·같은 템플릿·같은 도구 스키마를 쓴다. 샘플링이 필요 없고, 결정 지점당 후보 수만큼의 짧은 채점으로 끝난다(§3.3).
2. **환각·추론을 "결론 안정성"으로 통합하고 판정은 코드가 한다.** LLM은 handoff 경계의 발언을 atomic fact로 바꾸는 추출기(D7)로만 쓰고, 옳고 그름은 기록 검색·집합 비교가 결정한다. LLM-judge와 달리 근거 포인터(어느 스텝의 어느 도구 결과와 어긋났는지)가 항상 붙는다.
3. **탐지기는 정답·라벨을 입력으로 받지 않는다.** 임계값도 자기 분포의 백분위로 정하고, 라벨은 우리 실험의 평가에만 쓴다. 이것이 Align류 운영 솔루션에 바로 얹힐 수 있는 조건이다.
4. **성공 트레이스가 있다.** 귀속 벤치마크(실패 트레이스만)로는 잴 수 없는 오탐율·회복(transient vs decisive) 분석이 가능하다.

## 3. 제안 (Methodology)

### 3.1 실행 환경: Deep Agents 위의 두 그래프

```
[τ-bench airline]                                   [AIME 2026]
 customer(user_sim) ⇄ planner ──policy_checker──▶ think, 정책 wiki      planner ──solver──▶ run_python
                          └──db_agent──▶ 14 DB 도구                          └──verifier──▶ run_python (독립 재계산)
                     공유 FS: /case_notes.md (subagent가 append)               submit_answer
```

- subagent는 **이름을 가진 래퍼 도구**(`policy_checker`, `db_agent`, `solver`, `verifier`)로 planner에 바인딩된다. deepagents의 내장 `task` 도구는 대상 subagent를 인자(`subagent_type`, 자유 텍스트 뒤)에 두어 D1이 잴 수 없기 때문이다. 래퍼는 내장 `task`의 state 규약(copy-in/merge-out)을 복제해 공유 FS를 유지한다.
- 실행 모델 Qwen3-32B(vLLM, thinking off), 사용자 시뮬레이터도 같은 모델. 요약 미들웨어는 16k 토큰에서 명시 발동.
- **주 실험은 airline이다.** AIME 그래프는 결과 검토 후 보조 실험으로 내렸다: solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적어(라벨된 planner 오류 6건) planner→subagent 분해가 형식적이었다(§4.2.12).

### 3.2 완전 관측 기록

스텝(=LLM 호출)마다 HTTP 계층에서 요청 본문(messages, tools 스키마)과 응답 본문(content, tool_calls, 생성 토큰 logprobs, finish_reason)을 그대로 저장하고, 에이전트는 요청 헤더로 귀속한다. 도구 호출/결과는 SQLite, 공유 FS/todo는 스텝별 스냅샷, 요약 직전 원문도 보존한다. 이것이 탐지기의 **유일한 입력**이다.

### 3.3 감사 멀티에이전트(auditor): 모듈 정의

```
기록(steps.jsonl · tool_calls.sqlite · fs/) → 스텝 = [결정] → [행동: 도구 호출] → [발언]  (+ 스텝 사이의 handoff 경계)

 층            탐지기  검사                                                              대상            판정 주체
 ─────────────  ──────  ────────────────────────────────────────────────────────────────  ──────────────  ─────────
 결정          D1      후보 행동 위 분포: 1−p_actual · 1−confidence · 1−margin           planner·subagent 코드(LLM 없음)
                       + handoff 층(subagent에 넘길지 말지의 이진 엔트로피)              planner
 행동(도구)    D3      규칙 1 발언→필요 도구 · 규칙 2 지시→행동 · 규칙 3 인자 근거      주로 subagent   코드(LLM 없음)
                       + 호출 로그 검사 5종(error · empty · repeat · schema · ignored)
 handoff 경계  D7      지시→전제 · 보고→planner: atomic facts 보존도(fidelity)            planner↔subagent 8B 추출 + 코드 집합 비교
 발언·추론     —       (이번 연구에서 탐지기 없음 — 미해결, §4.3)                          —               —

 출력: 항목별 플래그 + 근거 포인터 → 트레이스 보고서(P4b) → 시스템 집계(P4c). 통합 점수 없음.
```

설계만 하고 구현하지 않은 선택 모듈: D8 축약 손실(요약 전후 atomic facts), D10 계획-행동 일치(todo/ledger vs 실제 호출), D6 재도출(정책 규칙 코드/재계산). 판정 주체 구분: **D1·D3 = 코드형**(LLM을 쓰지 않음), **D7 = 에이전트+코드**(8B가 발언을 atomic fact로 구조화, 판정은 코드).

**D1 — 행동 분포 confidence.** 결정 지점 = assistant 스텝. 후보 집합 A = 그 스텝에 바인딩된 도구 이름 ∪ {no_tool}. 정의: 렌더된 prefix를 고정하고 action 토큰만 바꿔 넣어 log P(a | context)를 얻는다(`<tool_call>\n{"name": "a`; 닫는 따옴표는 모델이 `",`를 한 토큰으로 내므로 제외). 실행: 같은 값을 `allowed_token_ids=[tᵢ]`로 강제한 1토큰 생성의 raw logprob 곱으로 계산해 prefix cache를 유지한다(§4.1에서 두 방식의 동일성 검증). 출력: 분포, 엔트로피 H, confidence = 1 − H/log|A|, p_actual, 1–2등 마진, 그리고 **2층 보고**(도구 층: 전체 A / handoff 층: {위임 래퍼} vs {비위임} 재정규화).

**D3 — tool-called + 도구 로그 검사.** 발언의 주장(예약번호·사용자ID·편명·금액·날짜·행동 동사; AIME는 수치·최종 답)마다 그 주장을 뒷받침할 도구 호출이 **그 이전에** 있었고 결과에 값이 있는지 규칙으로 판정. 도구 호출마다 5종 검사(에러, 빈 결과, 동일 호출 반복, 인자 스키마 위반, 에러 후 미인지)를 개별 플래그로. **규칙 2(지시→행동, 09-09 추가)**: handoff마다 planner 지시문이 요구하는 도구 군(조회·검색·예약·변경·취소·계산 등, airline 12군; AIME는 `run_python`)을 정규식으로 뽑아 그 subagent가 handoff 안에서 실제로 부른 도구와 대조하고, 하나라도 빠지면 subagent의 보고 스텝(마지막 스텝)에 1을 준다(`src/audit/d3_instruction.py`). 규칙 1이 "발언이 요구하는 근거"를, 규칙 2가 "지시가 요구하는 행동"을 본다. **규칙 3(도구 호출 인자 근거, 09-09 추가; 처음 D2 규칙 2로 만들었다가 D3로 이관)**: 스텝의 도구 호출 인자에서 식별자형 값(예약번호·사용자ID·편명·ISO 날짜·금액·출발/도착 공항 코드·이름)을 뽑아, 그 값이 에이전트에게 주어진 것(그 요청의 system/user/tool 메시지, 이전 고객 발화; 공항은 도시명, 날짜는 자연어 표기 허용)인지 확인한다. 인자는 구조화 JSON이라 LLM 추출이 없다(`src/audit/d3_args.py`). 점수 = 근거 없는 인자 값 비율.

**D7 — handoff 충실도.** 두 방향: 보고→planner 인용(subagent 보고의 atomic facts vs planner 다음 발언/행동 인자), 지시→전제(planner 지시 vs subagent 첫 발언의 전제 선언). 집합 차로 누락·추가·왜곡·fidelity.

### 3.4 라벨 없는 운영을 위한 설계

- 탐지기 입력에 정답·reward·라벨이 없다. 임계값은 항목별 자기 분포의 백분위(상위 5/10%).
- 모든 플래그에 근거 포인터가 붙어 사람 검수 루프(순위 → 소량 검수 → 임계값 갱신)에 들어간다.
- 전제 조건: **완전 관측 로깅 계약**(도구 결과, 모든 메시지, 모델이 실제 본 입력, 실행 모델 logprob 접근). 출력만 남는 로그에서는 D1·D3·D7이 동작하지 않는다.

## 4. 결과 및 평가 (Evaluation)

#### 4.1.1 실험 대상 시스템 (system under test)

Deep Agents(`deepagents 0.7.13`) 위의 두 그래프를 §3.1대로 실행한다. subagent는 전부 이름을 가진 래퍼 도구다.

| 항목 | τ-bench airline | AIME 2026 |

#### 4.1.5 D1 채점 방법과 타당성 검증

D1의 확률 `P(a | 문맥)`은 실행 후 같은 가중치(Qwen3-32B, 채점 전용 서버)로 **teacher-forced 재채점**하여 얻는다. 실행 기록에는 모델이 실제로 고른 행동의 logprob만 남고 나머지 후보의 값은 없기 때문이다. 후보 a의 토큰열은 `<tool_call>` 헤더 6토큰 + 이름 1~5토큰(7~11토큰)이며, 확률은 그 체인 전체 `∏ P(t_i | 문맥, t_<i)`다.

**채점 경로는 decode 경로다** (코드명 `stepwise`, `src/audit/d1.py`): 렌더된 prefix를 토큰 ID 배열로 고정하고, 후보 토큰을 한 개씩 `allowed_token_ids=[t_i]`로 강제한 1토큰 생성(`max_tokens: 1`)의 raw logprob(마스킹 전)을 읽어 합한다. 이 경로는 실행 시 모델이 토큰을 생성한 경로와 같고, vLLM prefix cache가 유지되어 호출당 마지막 토큰 한 step만 계산한다. `no_tool`은 첫 위치의 `1 − P(<tool_call>)`이다. 후보들의 공통 토큰 접두(헤더, 겹치는 이름 앞부분)는 한 번만 묻고 재사용한다(trie). 헤더 5토큰의 logp 합은 기록 974건에서 중앙값 −3×10⁻⁶, 최소 −0.0024로 무시할 수 있고, 실질적인 결정은 `<tool_call>` 여부와 이름 토큰에서 일어난다.

**재채점값 자체가 측정값이다.** 실행 시 기록된 logprob은 같은 가중치의 또 다른 bf16 계산 결과이므로 재채점보다 "참"에 가깝지 않고, 둘의 차이는 정확도가 아니라 두 추정치 사이의 반올림 잡음이다. 따라서 기록 logprob은 결과 지표로 쓰지 않고, **렌더 정합 검사**에만 쓴다: 결정 지점마다 기록의 생성 토큰열에서 `<tool_call>` 위치를 찾아 그 뒤 토큰열이 실제 선택 후보의 토큰열과 일치하는지 확인하고(불일치나 수 단위의 logp 이탈은 채팅 템플릿·도구 스키마 렌더 버그를 뜻한다), 정합 비율 한 줄만 보고한다. 실행 시 `logprobs` 옵션은 생성 토큰 ID를 받기 위한 채널로 켜 둔다(vLLM 0.9.2에는 `return_token_ids`가 없다). 결정 지점은 모델이 실제로 생성한 토큰열 위에 놓이며, 기록된 logprob 값 자체는 쓰지 않는다. 기록이 없는 실행은 응답 텍스트를 다시 토큰화한다(60회 검사에서 토큰 ID 완전 일치 467/471). 같은 요청도 prefix KV 블록이 다시 계산되는 시점에 따라 logp가 약 0.002(고확률 토큰), confidence가 약 0.005 흔들리는 **재현성 하한**이 있으며(같은 캐시 상태에서는 완전히 재현됨), 이것이 D1 값의 유효 자릿수다.

설계 초기에는 prefill 경로(`prompt_logprobs`, 코드명 `m2`)를 정의로 두고 decode 경로와의 분포 일치(|Δp| ≤ 0.01, 95%)를 게이트로 삼았다. 배치 1 검사에서 두 경로의 일치는 62%였으나, prefill 경로 자체도 기록 logprob과 같은 크기로 어긋났다(133지점, 확률 0.01 이내 86.5%, 최대 0.09). 즉 게이트가 잰 것은 두 재채점 경로 사이의 bf16 반올림 차이였고, 어느 경로도 다른 경로의 기준이 될 수 없다. 그래서 게이트를 철회하고 decode 경로 단일 방법으로 확정했다(사용자 결정, 09-09 04:12). prefill 경로 부분 채점(211지점)은 비교 표본으로만 남긴다(`audit/d1_m2_partial.jsonl`).

후보 집합 A = 그 스텝 요청 본문의 `tools` 이름 ∪ `{no_tool}`. 모델이 바인딩되지 않은 이름을 호출한 경우(환각 도구 이름)에는 그 이름을 **사후에 A에 추가해** 채점한다 — 그러지 않으면 실제 행동의 확률이 정의되지 않는다. `user_sim`·`summarizer` 스텝은 결정 지점이 아니다. 채점 서버의 24576 토큰을 넘는 prefix는 `d1_unscored.json`의 `prefix_too_long` 버킷으로 빠진다.

### 4.2 결과

#### 핵심 결과 (요약)

이 절의 결론은 세 문장이다. 아래 소절들은 이 세 문장의 근거와 상세이며, **본문 수치는 모두 주 실험 τ-bench airline(30회)**의 것이다. AIME 2026(30회)은 보조 실험으로 §4.2.12에 따로 둔다. 여기서 쓰는 두 용어만 먼저 적는다: **AUROC**는 오류 스텝과 깨끗한 스텝을 무작위로 하나씩 뽑았을 때 오류 스텝의 점수가 더 높을 확률(0.5 = 우연, 1 = 완벽)이고, **decisive 스텝**은 실패한 실행마다 라벨러가 하나 지목한 "실행을 실패로 이끈 스텝"이다. 나머지 용어는 §4.2.0.

**1. planner의 결정 불안정(D1)은 실패를 예고한다.** planner가 "다음에 누구를, 어느 도구를 부를지" 고른 지점에서 실행 모델의 확률 분포를 재계산하면, 실제로 실행된 행동의 확률이 낮았던 결정(1 − p_actual)이 decisive 스텝을 깨끗한 스텝과 **0.75** [0.61, 0.86]로 구별한다. 전체 오류 스텝에 대해서는 0.63 [0.54, 0.71]이다. 실행 단위로 보면, 실행 하나에서 가장 뜻밖이었던 결정 하나의 크기가 실행 성패를 0.81 [0.63, 0.96]로 가른다.

**2. subagent에서는 같은 방법이 작동하지 않고, 기록 대조 검사가 그 자리를 맡는다.** subagent의 실수는 "어느 도구를 부를까"의 흔들림이 아니라, 확신을 갖고 지어낸 값으로 도구를 부르거나 확신을 갖고 도구 없이 답하는 것이라 D1에는 보이지 않는다(decisive AUROC 0.36). 지어낸 값은 발언이 아니라 **도구 호출 인자**에 있었고, 인자 값이 에이전트에게 주어진 것인지 대조하는 D3 규칙 3이 subagent에서 **0.68** [0.58, 0.78]이다 — 라벨된 환각성 오류 29건 중 23건을 잡고 플래그한 스텝 10개 중 8개가 실제 오류다(FPR 2 %에서 recall 0.38). "발언이 요구하는 도구를 불렀는가"를 보는 D3 규칙 1은 decisive 스텝에서 0.66 [0.46, 0.83]이나 CI가 넓다. handoff 경계의 값 보존(D7)은 약했다. **값은 기록에 있는데 결론이 틀린 오류(추론 오류 층)는 이 연구의 어느 검사도 잡지 못하며**, 이것이 남은 가장 큰 미해결 항목이다(§4.3).

**3. 탐지기 성능은 탐지기 자체보다 "어느 역할에 붙였나"로 갈린다.** 같은 D1이 planner에서 0.63–0.75, subagent에서 0.5 아래다. 보조 실험(AIME)은 이 대비를 도메인 축으로 다시 보여 준다: 같은 planner D1이 트레이스 수준에서 airline 0.81, AIME 0.34로 뒤집히고, 같은 D3 반복 호출 검사가 AIME 정밀도 0.86, airline 0.22다(§4.2.12). 감사 파이프라인은 모든 스텝에 모든 항목을 돌리는 구조가 아니라, 역할과 도메인에 항목을 배정하는 라우팅으로 짜야 한다(§4.3).

| 항목 | 역할 (airline) | AUROC 전체 오류 [95 % CI] | AUROC decisive [95 % CI] | 판정 |
|---|---|---|---|---|
| D1 1 − p_actual | planner | 0.63 [0.54, 0.71] | **0.75 [0.61, 0.86]** | 작동 |
| D1 1 − p_actual | subagent | 0.54 [0.44, 0.63] | 0.36 [0.21, 0.51] | 신호 없음 |
| D3 규칙 3 인자 값 근거 | subagent | **0.68 [0.58, 0.78]** | n/a (양성 1) | 환각(지어낸 ID) 탐지에 작동, 정밀도 높음 |
| D3 규칙 1 필요 도구 미충족 | subagent | 0.55 [0.47, 0.62] | 0.66 [0.46, 0.83] | decisive에 약한 신호, CI 넓음 |
| D3 규칙 2 지시→행동 | subagent | 0.66 [0.53, 0.77] | 0.47 (양성 5, 판단 불가) | 전체 오류에 약한 신호 |
| D7 보고→planner | planner | 0.59 [0.47, 0.72] | 0.60 [0.40, 0.78] | 약함 |
| D7 지시→전제 | planner | 0.40 [0.25, 0.55] | 0.35 [0.13, 0.61] | 가설과 반대, 서술용 |

#### 4.2.0 용어

아래 표들에 쓰는 용어를 먼저 정리한다. 지표의 계산 정의와 모집단은 §4.1.4에 있으므로 여기서는 읽는 데 필요한 뜻만 적는다.

- **결정 지점**: planner 또는 subagent가 다음 행동을 고른 스텝 하나. `user_sim`·`summarizer` 스텝은 제외.
- **후보 집합 A**: 그 스텝에 바인딩된 도구 이름들 + `no_tool`. 모델이 호출한 이름이 A에 없으면 사후에 추가한다.
- **dist**: A 위의 정규화 확률. 후보별 토큰열의 조건부 확률을 정규화한 것(§4.1.5).
- **p_actual**: dist에서 실제로 실행된 행동의 확률. **1 − p_actual**은 "실제 선택이 얼마나 뜻밖이었나".
- **confidence**: 1 − (dist의 엔트로피 / log₂|A|). 분포가 한 후보에 몰리면 1, 균등이면 0. 분산이 아니라 정규화 엔트로피다. **1 − confidence**는 "분포가 얼마나 퍼졌나".
- **margin**: dist의 1등 − 2등. 점수는 **1 − margin**.
- **handoff 층 (D1_handoff)**: planner의 결정 지점에서 dist를 "subagent에 넘긴다(래퍼 호출)" vs "그 외(직접 도구·`no_tool`)"의 둘로 합친 뒤 계산한 이진 엔트로피 H2. "넘길지 말지"의 불확실성이며, 누구에게 넘기는지는 보지 않는다.
- **D3 규칙 1 / 2 / 3**: 규칙 1은 "발언의 숫자 주장에 필요한 도구 근거가 있는가"(스텝 단위, 0/1), 규칙 2는 "planner 지시가 요구한 도구 군을 handoff 안에서 불렀는가"(보고 스텝에 부여, 0/1), 규칙 3은 "도구 호출 인자의 식별자형 값 중 에이전트에게 주어지지 않은 것의 비율"(0~1).
- **오류 이벤트**: 라벨러가 표시한 스텝 단위 오류(decisive / transient / error 세 클래스). 한 실행에 여러 개 있을 수 있다.
- **decisive 스텝**: 실패한 실행마다 라벨러가 하나 지목한 "실행을 실패로 이끈 스텝". **cascade 스텝**(decisive 이후 그 결과로 따라 나온 스텝)은 양성·음성 어디에도 넣지 않는다.
- **전체 오류 AUROC vs decisive AUROC**: 양성 집합만 다르다. 전체 오류 = 모든 오류 이벤트 스텝, decisive = decisive 스텝만. 음성은 둘 다 같은 clean 스텝.
- **트레이스 수준 max / mean**: 실행 하나의 점수를 스텝 점수의 최댓값 또는 평균으로 요약하고, 실행 성공 여부를 양성으로 하는 AUROC. 역할 스코프 채점률 80% 미만인 실행은 제외(커버리지 규칙).
- **귀속 정확도**: 점수 argmax 스텝이 라벨된 decisive 스텝과 정확히 같은가(exact) / 앞뒤 한 스텝 안인가(±1) / 같은 에이전트인가(agent).
- **recall@FPR10, 탐지 지연**: clean 스텝의 10%만 잘못 울리는 임계값에서 잡은 오류 비율, 그리고 decisive 이후 임계값을 처음 넘기기까지의 스텝 수.
- **백분위 임계값 vs 라벨 최적**: 라벨 없이 점수 상위 5%·10%를 자르는 규칙과, 라벨로 Youden J를 최대화한 임계값의 recall·FPR 비교.
- **매칭 부표**: D1과 D3 규칙 1이 모두 채점한 스텝 교집합에서만 다시 계산한 AUROC.
- **subtag**: 라벨의 서술용 태그(hallucination_like / handoff_induced / reasoning_like / none). 판정에 쓰지 않는다(§1.2).

D3 규칙 1은 전체 오류에서는 0.55지만 decisive 스텝에 대해 0.66 [0.46, 0.83]으로, 라벨된 결정적 실패 지점 중 "필요한 도구를 부르지 않은 스텝"이 있음을 보이나 양성이 7개라 CI가 0.5에 닿는다. 전체 오류에서 낮은 이유는 규칙("숫자 주장 → 도구 근거 필요")이 거친 근사라서다(아래 수치는 두 도메인 합산): 도구를 부르지 않은 subagent 스텝(cascade 제외 117개)의 3분의 2는 최종 보고 등 정당한 무도구 발언이고, D3가 미충족으로 찍은 45개 중 오류는 19개(42%)다. 도구를 부른 스텝과 부르지 않은 스텝의 라벨 오류율은 같다(32%). 즉 "도구를 안 불렀다"는 신호가 아니고 "이 발언에 필요한 근거가 있는가"가 신호인데, 결정적 실패는 그 규칙에 정확히 걸리는 형태(조회 없이 값을 말함)라 decisive에서만 강하다.

**D3 규칙 2(지시→행동)**는 이 관찰에서 나온 검사로, 라벨을 본 뒤에 추가했지만 라벨을 입력으로 쓰지 않는 결정적 규칙이다(부록 A.14). 점수는 handoff의 보고 스텝에만 붙으므로 모집단이 규칙 1과 다르다(airline subagent 보고 스텝 127개). 전체 오류 0.66 [0.53, 0.77]로 규칙 1보다 낫지만, decisive는 양성 5개로 판단할 수 없고, 정규식이 지시문의 자연어("현재 가격을 조회")를 도구 군으로 옮기는 과정의 오탐이 남는다. 이 규칙이 강하게 작동한 곳은 보조 실험 AIME(decisive 0.78)인데, 그 이유는 §4.2.12에서 다룬다. D7 report→planner는 0.59 [0.47, 0.72], **D7 instruction→premise는 0.40으로 우연 아래**다: 지시문의 값이 subagent 첫 발언에 덜 보존될수록 오류일 것이라는 가설은 이 데이터에서 성립하지 않는다.

**D3 규칙 3(도구 호출 인자 근거)**는 결과 검토에서 나온 검사다(부록 A.16, A.18). 처음 설계의 발언 근거 검사(삭제된 D2: 발언 속 값이 기록에 있는가)는 hallucination_like로 라벨된 subagent 오류 49건 중 38건을 "값이 전부 근거 있음"으로 봤는데, 라벨을 보면 지어낸 값은 발언이 아니라 도구 호출 인자에 있었다(`get_user_details(user_id='rossi_123')`: 고객은 성 'Rossi'만 말했다). 인자를 대조하면 subagent에서 전체 오류 0.68 [0.58, 0.78]이고, 라벨된 환각성 오류 29건 중 23건을 잡으며, 플래그한 스텝 10개 중 8개가 실제 오류다(FPR 0.02에서 recall 0.375). decisive AUROC는 양성이 1개라 없다: 결정적 실패는 인자를 넣는 스텝이 아니라 보고 스텝에 찍히기 때문이고, 이 검사는 "지어낸 식별자"라는 오류 종류에 특화된 고정밀 검사로 읽는 것이 맞다. 근거 없는 값의 종류는 user_id 33, 공항 19, 금액 14, 날짜 12다(두 도메인 합산; AIME에는 식별자형 인자가 거의 없어 사실상 전부 airline이다). 발언 자체의 값을 대조하던 검사는 D3 규칙 1(숫자 주장 → 도구 근거)과 겹치고 신호가 없어(0.47) 모듈에서 뺐다(부록 A.18).

#### 4.2.3 트레이스 수준 AUROC

무엇을 재나: 실행을 스텝 점수의 max 또는 mean으로 요약했을 때 실패 실행을 구별하는 정도. 모집단 = `runs/index.csv`의 airline 31런(스모크 1건 포함) 중 역할 스코프 채점률 ≥ 80 %인 런(라벨 불필요).

| 항목 | 역할 | n_runs (실패 / 성공) | AUROC max [95 % CI] | AUROC mean [95 % CI] |
|---|---|---|---|---|
| D1 1 − p_actual | planner | 31 (25 / 6) | **0.813 [0.627, 0.960]** | 0.753 [0.580, 0.907] |
| D1 1 − confidence | planner | 31 (25 / 6) | 0.780 [0.593, 0.927] | 0.720 [0.553, 0.880] |
| D1 handoff 층 | planner | 31 (25 / 6) | 0.673 [0.507, 0.840] | 0.467 [0.240, 0.693] |
| D1 1 − p_actual | subagent | 31 (25 / 6) | 0.553 [0.273, 0.820] | 0.600 [0.360, 0.833] |
| D3 규칙 1 | subagent | 19 (13 / 6) | 0.506 [0.346, 0.712] | 0.372 [0.090, 0.679] |

성공 런이 6건뿐이라 CI가 넓다. planner D1은 트레이스 수준에서도 0.81(max)로, 실행 하나에서 가장 뜻밖이었던 planner 결정 하나의 크기가 성패를 가른다. subagent 항목은 모두 0.5 부근이다. D3의 planner 셀과 all-roles 셀은 "산출 불가"다: planner는 숫자 주장·도구 호출이 있는 스텝이 적어 채점률 80 %를 넘는 런이 1건이고, all-roles 스코프에서는 그 조건이 두 역할에 동시에 걸려 대부분의 런이 탈락한다. 트레이스 수준 지표는 이 데이터에서 항목 간 순위를 주장할 근거가 되지 못하며, planner D1의 방향 정도만 말할 수 있다. AIME에서는 같은 planner D1이 0.34로 뒤집힌다(§4.2.12).

#### 4.2.4 decisive 스텝 귀속 정확도

무엇을 재나: 점수 최댓값 스텝이 라벨 decisive 스텝과 얼마나 일치하는가. 모집단 = decisive_step이 있는 airline 실패 런 24건(역할 스코프에 채점 스텝이 있는 런만). 동점은 planner 우선 → 이른 스텝.

| 항목 | 역할 | n_runs | 정확 일치 | ±1 | 에이전트 일치 |
|---|---|---|---|---|---|
| D1 1 − p_actual | planner | 24 | 0.167 | 0.250 | 0.667 |
| D1 handoff 층 | planner | 24 | 0.208 | 0.292 | 0.667 |
| D1 1 − p_actual | subagent | 24 | 0.000 | 0.292 | 0.208 |
| D3 규칙 3 인자 근거 | subagent | 22 | 0.000 | 0.273 | 0.273 |
| D3 규칙 1 | subagent | 21 | 0.048 | 0.286 | 0.190 |
| D3 규칙 2 | subagent | 24 | 0.083 | 0.125 | 0.250 |
| D7 report→planner | planner | 23 | 0.174 | 0.217 | 0.652 |

스텝 정확 일치는 모두 0.21 이하다. D1은 순위(AUROC)는 있으나 "가장 불안정한 스텝 = decisive 스텝"은 아니며, ±1 허용에서도 0.25–0.29다. 에이전트 일치는 planner 항목이 0.65–0.67인데, airline 결정적 실패 24건 중 16건이 planner 스텝이라 planner 스코프 항목은 역할을 맞히기 쉽다. AIME에서는 D3 규칙 1의 정확 일치가 0.59로 예외적으로 높은데, 그 이유는 §4.2.12에서 다룬다.

#### 4.2.5 recall@FPR10과 탐지 지연

무엇을 재나: 거짓 양성률을 10 %로 묶었을 때 잡히는 오류의 비율과, 실패 런에서 그 임계값을 decisive 이후 처음 넘기는 시점. 모집단 = 스텝 AUROC와 같다(임계값은 같은 역할·도메인의 clean 스텝으로 정함).

| 항목 | 역할 | 임계값 | 달성 FPR | recall(전체 오류) | n_pos | n_crossed / n_failed | 지연 중앙값 (스텝) |
|---|---|---|---|---|---|---|---|
| D1 1 − p_actual | planner | 0.247 | 0.095 | 0.196 | 46 | 18 / 24 | 4.0 |
| D1 1 − confidence | planner | 0.333 | 0.095 | 0.174 | 46 | 16 / 24 | 5.5 |
| D1 handoff 층 | planner | 0.704 | 0.095 | 0.065 | 46 | 8 / 24 | 5.5 |
| D1 1 − p_actual | subagent | 0.294 | 0.100 | 0.146 | 48 | 12 / 24 | 3.0 |
| D3 규칙 3 인자 근거 | subagent | 0.100 | 0.022 | **0.375** | 24 | 9 / 24 | 3.0 |
| D7 instruction→premise | planner | 0.800 | 0.091 | 0.190 | 21 | 1 / 24 | 0.0 |

이진·동점이 많은 항목(D3 규칙 1·2, D7 report→planner)은 임계값이 최댓값(1.0)으로 밀려 FPR 0 · recall 0이 되므로 표에서 뺐다(D3는 §4.2.9의 검사별 정밀도·재현율로 본다). FPR 10 %에서 D1 planner의 recall은 0.20이고, 실패 런 24건 중 18건에서 decisive 이후 임계값을 넘겼으며 그 시점은 decisive로부터 중앙값 4스텝 뒤다. 즉 D1은 결정적 실패 "그 스텝"보다 그 직후의 흔들림을 잡는다. D3 규칙 3은 값이 거의 이진이라 FPR이 2 %에 그치면서 recall 0.375를 내는 고정밀 항목이다.

#### 4.2.6 임계값 실험: 백분위 vs 라벨 최적

무엇을 재나: 라벨 없이 정한 백분위 임계값이 라벨로 정한 최적 임계값에 비해 recall·FPR을 얼마나 잃는가. 모집단 = 백분위 풀은 airline 31런의 채점된 스텝 전체, FPR·recall은 라벨된 airline 스텝. `Δ`는 같은 셀의 라벨 최적(Youden J 최대) 행과의 차이.

D1의 라벨 최적 임계값은 1 − confidence 기준 0.003–0.007, 즉 **confidence가 0.995 아래인 결정을 전부 플래그**하는 지점이고 그때 FPR은 0.34–0.65다. 분포의 대부분이 confidence > 0.99에 몰려 있어 "상위 5–10 %"만 잡는 백분위 규칙은 recall을 0.04–0.17로 떨어뜨린다(planner Δ recall −0.74 ~ −0.87). D1은 순위 신호(AUROC)로는 쓸 수 있지만, 낮은 FPR을 유지하는 고정 임계 알람으로는 오류의 대부분을 놓친다. D7은 값이 소수의 이산 수준에 몰려 p95와 p90이 같은 임계값에 걸린다.

#### 4.2.8 매칭 부표

무엇을 재나: 항목 간 모집단 차이를 없앤 상태의 AUROC. 모집단 = D1과 D3 규칙 1이 동시에 채점한 라벨 스텝의 교집합(D1 ∩ D3; 계산 시점에는 삭제된 D2도 조건에 들어 있었으나 D2는 D3 규칙 1과 거의 같은 스텝을 채점하므로 교집합은 사실상 같다). 이 교집합(airline, 사실상 subagent 스텝 195개; planner는 양성 1개)에서 다시 계산한 AUROC(전체 오류)는 D1 1 − conf 0.560 [0.462, 0.663], D3 규칙 1 0.546 [0.471, 0.625]로, §4.2.2의 subagent 셀과 CI가 겹친다. subagent 스텝에서는 모집단 차이가 항목 간 비교를 왜곡하지 않는다. planner 스텝은 D3가 거의 채점하지 않아 이 방식의 비교가 불가능하다.

#### 4.2.9 D3 도구 검사 vs `category = tool` 라벨

무엇을 재나: D3의 이진 검사 다섯 종 각각이 tool 범주 라벨 이벤트와 스텝 단위로 겹치는 정밀도·재현율. 모집단 = 라벨된 airline 비보조 스텝 826개(cascade 포함); 어떤 도구 호출이든 그 검사에 걸리면 플래그.

|---|---|---|---|---|---|
| error (미회복 오류 결과) | 82 | 83 | 45 | **0.542** | **0.549** |
| repeat (같은 호출 반복) | 82 | 78 | 17 | 0.218 | 0.207 |

#### 4.2.10 subtag 서술 분석

무엇을 재나: subtag별로 어느 항목의 점수가 높았는가(서술 통계, 판정 아님 — §1.2). 모집단 = 라벨된 오류 스텝 중 그 항목이 채점한 스텝. **이 표는 두 도메인 합산**이다(`eval/subtags.md`는 도메인을 나누지 않음). `mean`은 그 subtag의 오류 스텝에서 항목 점수의 평균, `flagged`는 항목의 p90 임계값 이상인 비율이다.

| subtag | n_steps | D1 1 − conf mean / flagged | D3 규칙 1 mean / flagged | D3 규칙 3 mean / flagged | D7 report→planner mean / flagged |
|---|---|---|---|---|---|
| hallucination_like | 69 | **0.122** / 0.159 | 0.500 / 0.500 (n = 36) | **0.718** / – (n = 29) | 0.800 / 0.000 (n = 1) |
| handoff_induced | 93 | 0.099 / 0.151 | 0.250 / 0.250 (n = 4) | 0.025 / – (n = 37) | **0.664** / 0.226 (n = 62) |
| reasoning_like | 92 | 0.019 / 0.022 | **0.615** / 0.615 (n = 78) | 0.000 / – (n = 10) | 0.913 / 0.500 (n = 2) |
| none | 180 | 0.061 / 0.083 | 0.184 / 0.184 (n = 125) | 0.075 / – (n = 39) | 0.493 / 0.000 (n = 4) |

항목마다 반응하는 subtag가 다르다. D1 불안정성은 hallucination_like·handoff_induced 스텝에서 높고(0.10–0.12) reasoning_like 스텝에서는 0.02로 거의 0이다 — 추론 오류가 나는 스텝에서 모델은 흔들리지 않는다. D3 규칙 1은 reasoning_like에서 0.62로 가장 높은데, 이 subtag의 대부분이 AIME 스텝이고 그 추론 오류가 대개 검증 도구를 부르지 않은 스텝과 겹치기 때문이다(airline만의 reasoning_like는 30건). D3 규칙 3(인자 근거)은 hallucination_like에서 평균 0.72, 다른 subtag에서 0.00–0.07로 가장 선택적으로 반응한다(값이 거의 이진이어서 p90 임계값 0이라 flagged 비율은 의미가 없어 표기하지 않았다). D7 report→planner의 missing 비율은 handoff_induced에서 0.66으로 높다. 라벨된 오류 스텝 172개 중 어느 항목이든 p90 임계값으로 플래그한 것은 84개(48.8 %)다.

#### 4.2.12 보조 실험: AIME 2026

무엇인가: 같은 하네스로 30회 실행·라벨·채점한 수학 도메인이다. 설계 시점에는 airline과 동격의 두 번째 도메인이었으나, 결과 검토에서 **멀티에이전트 과제로 부적합**하다고 판단해 보조 실험으로 내렸다(사용자 결정, 09-09 06:30; 부록 A.17). 이 규모에서 관찰된 이유는 세 가지다. (1) solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적다 — 라벨된 planner 오류 이벤트가 6건뿐이다(airline 100건). (2) subagent의 행동이 사실상 강제된다 — solver·verifier는 `run_python`을 부르거나 보고하는 것 외의 선택지가 없다. (3) 여러 셀이 airline과 반대 방향이다 — planner D1의 트레이스 수준 AUROC가 airline 0.81, AIME 0.34다. planner→subagent 분해가 형식적이어서 "handoff·도구 선택의 불안정"이라는 가설이 잴 대상 자체가 적다. 따라서 AIME는 역할 × 도메인 교훈의 대비 사례로만 쓴다. 모든 수치는 `eval/metrics.md`에 그대로 있다.

### 4.3 해석과 한계 (Discussion)

**작동한 것.** 주 실험 airline에서 D1의 불안정성 지표는 planner 결정에서 라벨된 오류를 구별한다(1 − p_actual 0.63, decisive 0.75; 트레이스 수준 max 0.81). planner는 매 스텝 "어느 subagent 또는 도구를 부를지"를 여러 후보 사이에서 정하는 자리라, 실패가 실제로 결정의 흔들림으로 나타나는 곳이다. 세 점수(1 − confidence, 1 − p_actual, margin) 중 1 − p_actual이 일관되게 가장 높은데, 결정적 실패의 상당수가 "분포는 뾰족한데 그 뾰족한 쪽이 아닌 행동을 실행한" 경우임을 뜻한다. subagent 층에서 작동한 것은 D3 규칙 3(도구 호출 인자의 근거)다: 전체 오류 0.68, 플래그 스텝의 80 %가 실제 오류, 라벨된 환각성 오류 29건 중 23건 — "지어낸 식별자로 도구를 부른다"는 오류 종류에 특화된 고정밀 검사다. D3 규칙 1은 decisive에서 0.66이나 양성 7개로 CI가 0.5에 닿고, D3의 error 검사는 tool 라벨과 정밀도·재현율 0.54 / 0.55로 겹친다.

**작동하지 않은 것.** subagent 스텝에서 D1은 0.54, decisive에서는 0.36으로 우연 이하다. 가장 그럴듯한 기제는 subagent의 다음 행동이 planner의 지시문에 의해 거의 강제된다는 점이다: `db_agent`는 조회를 부르는 것이 정해져 있어 분포가 뾰족하고(confidence > 0.99가 subagent에서 더 많다), 오류는 "어느 도구를 부르는가"가 아니라 "무슨 인자로, 무슨 결론으로"에서 난다. D1이 재는 것은 후보 집합 위의 분포이므로 그 층의 오류는 원리적으로 보이지 않는다. subagent의 no_tool은 구조상 "보고하고 planner로 복귀"라(두 도메인 260/260건 다음 스텝이 planner), 문제는 끝내기로 한 결정의 흔들림이 아니라 끝내기 전에 지시받은 일을 했는가다. 이를 라벨 없이 가르는 검사가 **지시→행동 대조**(D3 규칙 2)인데, airline에서는 전체 오류 0.66에 그치고 decisive는 양성 5개로 판단할 수 없다 — 지시문의 자연어를 도구 군으로 옮기는 규칙의 정밀도가 병목이라, 다음 단계는 그 매핑을 도구 스키마 설명에서 자동으로 만드는 것이다. 발언 속 값의 근거를 보던 검사(삭제된 D2)는 0.47로 신호가 없었다. 이유는 두 가지다. 첫째, 지어낸 값은 발언이 아니라 도구 호출 인자에 있었고(환각성 오류 49건 중 38건), 그 자리를 보는 D3 규칙 3은 작동한다. 둘째, "값이 기록에 있는가"는 값은 전부 기록에 있는데 결론이 틀린 추론 오류를 잡을 수 없고, 반대로 기록에 없는 값을 말하는 정당한 재서술(단위 변환, 합계)을 플래그한다. 그래서 D2는 D3 규칙 1과 겹치는 부분만 남기고 모듈에서 뺐다(부록 A.18). **그 결과 "값은 맞는데 결론이 틀린" 추론 오류 층(airline 라벨의 reasoning_like 30건, 두 도메인 합산 92건)은 이 연구의 어느 검사도 담당하지 않는다.** 이것이 남은 가장 큰 미해결 항목이다. D7 instruction→premise는 0.40으로 가설과 반대다: subagent가 첫 발언에서 지시문의 값을 되풀이하지 않는 것은 정상 handoff에서도 흔하고(평균 fidelity 0.74), AUROC의 부호는 반대 경향(문제가 있는 handoff에서 오히려 더 되짚음)을 시사하지만 이 데이터로 확인한 것은 아니다. 이 방향은 신호가 아니라 서술 통계로만 남긴다.

**임계값의 실용성.** D1은 순위 지표로는 쓸 수 있지만 고정 임계 알람으로는 약하다. 라벨 최적 임계값은 confidence 0.995 부근, 즉 "조금이라도 흔들린 결정은 전부"이고 그때 FPR은 0.34–0.65다. 분포의 대부분이 confidence > 0.99에 몰린 상태에서 상위 5–10 % 백분위 규칙은 recall을 0.04–0.17로 떨어뜨린다. 운영에서 D1은 트레이스를 검토 우선순위로 정렬하거나 다른 항목과 교차할 때 쓰고, 단독 알람 임계값은 두지 않는 편이 맞다. 탐지 지연(중앙값 4스텝)과 회복 궤적(오류 다음 스텝에 정점)은 같은 이야기를 한다: D1이 잡는 것은 결정적 실패 그 스텝이 아니라 그 직후 planner가 상황을 수습하려 할 때의 흔들림이다. 반대로 D3 규칙 3은 거의 이진인 고정밀 항목이라 고정 임계 알람으로 바로 쓸 수 있다(FPR 2 %, recall 0.38).

**측정 잡음이 뜻하는 것.** 같은 요청도 KV-cache 상태에 따라 logp가 약 0.002, confidence가 약 0.005 흔들린다(§4.1.5). 이 크기 아래의 차이는 신호가 아니다. 라벨 최적 임계값(1 − confidence 0.003–0.007)이 바로 이 잡음 수준에 있다는 점은, 그 임계값이 실제로는 "confidence가 정확히 1이 아닌 결정"을 고르는 규칙이며 재현 가능한 경계가 아님을 뜻한다. D1의 유효 자릿수는 소수 둘째 자리까지이고, 항목 간 AUROC 차이도 부트스트랩 CI가 겹치면 순위를 주장하지 않는다.

**감사 MAS 설계에 대한 교훈.** 가장 큰 결과는 항목의 성능이 항목 자체보다 **역할 × 도메인**에 의해 갈린다는 점이다. 역할 축은 주 실험 안에서 보인다: 같은 D1이 planner에서 0.63–0.75, subagent에서 0.5 아래이고, subagent 층은 D3 규칙 3이 맡는다. 도메인 축은 보조 실험이 보여 준다: 같은 planner D1이 트레이스 수준에서 airline 0.81, AIME 0.34로 뒤집히고, 같은 D3 repeat 검사가 AIME 정밀도 0.86, airline 0.22다(§4.2.12). 감사 파이프라인은 "모든 스텝에 모든 항목"이 아니라 역할과 도메인에 항목을 배정하는 라우팅으로 짜야 한다: planner 결정에는 D1, subagent의 도구 층(인자·필요 도구·지시 충족)에는 D3(도메인별 규칙 선택)를 두고, D7은 handoff 경계의 서술 프로파일로만 쓴다. 발언의 결론 층은 비어 있다. §4.2.11의 시스템 단위 집계가 그 라우팅 결과를 에이전트·엣지 단위로 보여 주는 출력이다. 라벨 30런(airline)으로는 셀당 표본이 작아 이 배정의 세부는 잠정적이며, 항목 간 결합(교차 플래그)은 라벨을 늘린 뒤에 평가해야 한다.

#### 한계 (Limitations)

- **라벨러가 사람이 아니다.** 어노테이터는 Claude 서브에이전트이고, 품질 관리도 같은 모델 계열의 다른 인스턴스가 했다. 스팟체크의 decisive 일치 6/6은 높지만 이벤트 집합 Jaccard 0.563은 "무엇을 오류로 셀 것인가"의 자유도가 크다는 뜻이며, RUBRIC §5b는 그 자유도를 recall 쪽으로 고정한 **규약**일 뿐 정답이 아니다. 모델-모델 일치도는 사람-모델 일치도의 상한도 하한도 아니다. 라벨러는 `summary.md`만 읽으므로 요약이 흘린 것은 라벨에도 없다.
- **주 실험은 30회 규모다.** 본문 수치는 airline 30회(성공 6 / 실패 24)에서 나왔다. 항목 × 역할로 쪼개면 셀당 유효 표본이 작고(decisive 양성 planner 16, subagent 8) 부트스트랩 CI가 넓다. 항목 간 순위를 CI 겹침 없이 주장할 근거로는 부족하며, 성공 6건 때문에 트레이스 단위 지표는 특히 불안정하다.
- **주 근거가 도메인 하나다.** 결론의 근거는 τ-bench airline(정책·DB 조회) 하나이고, 두 번째 도메인으로 실행한 AIME 2026은 멀티에이전트 과제로 부적합해 보조 실험으로 내렸다(§4.2.12). 검색·코딩·장기 실행 워크플로는 다루지 않았다. 따라서 "역할 배정이 성능을 가른다"는 교훈은 한 도메인 안의 관찰이고, 도메인 축의 대비(§4.2.12)는 부적합한 도메인과의 대비라 일반화 근거로는 약하다. 두 도메인의 실패 양상(정책 위반 vs 빈 stdout 위조·반복 루프)이 서로 달라 도메인 평균(합산 셀)은 해석 가치가 낮다.
- **단일 실행 모델과 로깅 계약 전제.** 실행·시뮬레이터·채점이 모두 Qwen3-32B 한 계열이다. 다른 모델 계열에서 D1 분포가 같은 모양일 보장이 없다. 전제 조건은 **완전 관측 로깅 계약** — 도구 결과, 모든 메시지, 모델이 실제로 본 입력, 그리고 실행 모델의 logprob 접근이다. 출력만 남는 로그에서는 D1·D3·D7이 아예 동작하지 않으므로, 이 결과의 프로덕션 **일반화**는 불가하다.
- **bf16 로짓 양자화.** D1 확률은 채점 서버의 bf16 계산 결과이며, 실행 서버나 prefill 경로로 계산하면 반올림이 달라 logp가 0.1 안팎, confidence가 0.005 안팎 흔들린다. 어느 계산도 다른 계산의 기준이 아니므로 이 크기를 측정 잡음으로 두고 임계값 민감도를 함께 보고한다. 절대 logp 값을 신호로 쓰는 확장(예: perplexity 임계)은 정당화되지 않는다.
- **D1이 덮는 범위는 유한한 다음 행동 결정뿐이다.** 도구·subagent 선택처럼 후보 집합이 닫힌 지점에만 쓰고, 텍스트 환각에는 쓰지 않는다(과신 환각에 취약하므로 — §2). 자유 텍스트 속 값의 신뢰도는 D3 규칙 1·3의 기록 대조가 담당하고, 결론 자체의 옳고 그름은 이 연구에서 담당 검사가 없다.
- **D1 커버리지가 100%가 아니다.** 채점 서버의 24576 토큰을 넘는 prefix(`prefix_too_long`), 경계 단언 실패, 시간 컷으로 미채점 결정 지점이 남고 `d1_unscored.json`에 유형별로 집계된다. 트레이스 단위 지표는 역할 스코프 채점률 80% 미만인 런을 아예 제외하므로, 커버리지 손실은 모집단 축소로도 나타난다.
- **추출기(8B) 오류가 하류로 전파된다.** D7은 Qwen3-8B가 handoff 양쪽 발언을 atomic fact로 구조화한 결과 위에서 판정한다(D1·D3는 LLM을 쓰지 않는다). 추출 실패는 D7의 오탐/미탐으로 그대로 넘어가며, **추출기 민감도 실험(다른 크기·다른 프롬프트로 재추출)은 실행하지 않았다.**
- **τ-bench 사용자 시뮬레이터를 대체했다.** 원본의 litellm 경로 대신 같은 모델을 쓰는 raw httpx **시뮬레이터**(`src/data/tau_user.py`)로 바꿔 요청 본문 캡처와 thinking off / temperature 0을 보장했다. 시스템 프롬프트와 인터페이스는 같지만 원본과의 동등성은 약해졌고, τ-bench 공개 성공률과 직접 비교할 수 없다.
- **환각 도구 이름을 사후에 후보 집합에 넣는다.** 모델이 바인딩되지 않은 이름을 호출하면 그 이름을 A에 추가해야 실제 행동의 확률이 정의된다. 이는 감사 시점에만 가능한 조작이며, 실시간 가드레일에서는 후보 집합을 사전에 닫을 수 없다.
- **D7 방향 2는 주입 프롬프트 준수도에 의존한다.** subagent가 첫 발언에서 전제를 3–5개로 선언하도록 시스템 프롬프트로 강제했지만, 모델이 그 지시를 지키지 않으면 비교 집합이 비고 방향 2는 NA가 된다. 준수율이 낮으면 방향 1(보고→인용)만 보고한다.
- **`files` 삭제가 전파되지 않고 todo는 공유되지 않는다.** 공유 파일시스템은 delta reducer 기반이라 subagent의 파일 **삭제**는 planner state로 병합되지 않는다(`docs/notes/deepagents_probe.md`). `todos`는 deepagents의 state 규약상 양방향 제외다. 두 경로 위의 실패는 이 기록에 남지 않는다.
- **순차 위임 그래프만 검증했다.** planner → subagent의 **순차** orchestrator-worker 한 형태이며, 병렬 fan-out, 에이전트 간 직접 통신, 순환 그래프, 다중 planner는 실행하지도 감사하지도 않았다.
- **선택 모듈은 미구현이다.** D8(축약 손실), D10(계획-행동 일치), D6(재도출)은 §3.3에 설계만 있고 **미구현**이다. LLM-judge 베이스라인의 구현 여부는 §4.2를 참조한다. 따라서 "코드 판정 vs judge" 비교의 강도는 §4.2가 보고하는 범위로 한정된다.

### 4.4 기대 효과 (Expected Impact)

Align류 운영 솔루션(성공·실패가 섞인 대량의 에이전트 로그를 사후에 보는 제품)에 그대로 얹히는 것을 목표로 설계했다.

**1. 라벨 없는 순위 + 근거 포인터 → 사람 검수 루프.** 탐지기는 정답·reward·라벨을 입력으로 받지 않는다. 운영 로그에 그대로 돌리면 스텝마다 항목별 신호와 근거 포인터(어느 스텝의 어느 도구 결과·어느 보고와 어긋났는지)가 나오고, 검수자는 트레이스를 처음부터 읽는 대신 상위 몇 %의 스텝만 열어 확인한다. 확인 결과는 다시 임계값과 rubric으로 돌아간다 — 순위 → 소량 검수 → 임계값 갱신의 닫힌 루프이며, 각 회차의 비용이 검수한 스텝 수에 비례한다.

**2. 트레이스가 아니라 에이전트 시스템을 평가한다.** 시스템 집계 보고서는 에이전트(역할)별로 결정 수·저신뢰 결정 비율·근거 없는 인자 비율·도구 검사 5종 비율을, handoff 엣지별로 건수·충실도 평균·저충실도 비율·누락/왜곡 상위 키를 낸다. "이 시스템은 어디가 약한가"에 대한 답이 트레이스 목록이 아니라 **역할과 엣지 위의 프로파일**로 나오므로, 프롬프트 수정·도구 스키마 변경·subagent 분리 같은 조치의 대상이 바로 지목된다. 개별 트레이스에 통합 점수를 붙이지 않는 것도 같은 이유다 — 통합 점수는 조치로 번역되지 않는다.

**3. 로깅 계약을 제품 요구사항으로 승격시킨다.** 이 파이프라인이 돌기 위해 고객 시스템이 남겨야 하는 것은 명확하다: (a) 스텝(LLM 호출)마다 **모델이 실제로 본 입력 전체** — 렌더된 메시지와 도구 스키마, (b) 응답 본문 — content, tool_calls, finish_reason, (c) 도구 호출의 인자와 **결과 원문**, (d) 공유 상태(파일·todo)의 스텝별 스냅샷과 요약 직전 원문, (e) 호출을 낸 에이전트 식별자, (f) D1을 쓰려면 실행 모델의 logprob 접근(자체 호스팅이거나 logprobs를 주는 API). (a)–(e)만으로 D3·D7이 돌고, (f)가 더해질 때 D1이 켜진다. 이 목록은 곧 온보딩 체크리스트이자 SDK 계측의 사양이다.

**4. 라벨 0에서 시작할 수 있다.** 임계값은 항목별 자기 분포의 백분위(상위 5/10%)로 정한다. 새 고객·새 도메인에 라벨이 한 건도 없어도 첫날부터 순위가 나오고, 검수가 쌓이면 그 셀에서만 라벨 최적 임계값으로 옮겨가면 된다. §4.2의 백분위 vs 라벨 최적 비교가 이 부트스트랩에서 얼마를 잃는지를 재는 실험이다.

**5. 판정 주체가 코드라 감사 가능하다.** LLM은 handoff 경계의 발언을 구조로 바꾸는 추출기(D7)로만 쓰고, 옳고 그름은 기록 검색·집합 비교가 결정한다. 판정 규칙이 코드라서 재현되고, 고객이 이의를 제기하면 근거 포인터를 그대로 보여줄 수 있으며, 규칙 변경의 영향 범위를 재실행으로 확인할 수 있다. LLM-judge 기반 제품이 겪는 "판정이 바뀌었는데 왜 바뀌었는지 모른다"는 문제가 구조적으로 발생하지 않는다.

## 부록 A. 스펙 이탈·정정 각주

계획 §9의 12건. 형식: **스펙 → 실행 → 이유**.

1. **채점 호출의 `max_tokens=0` → `max_tokens=1`.** vLLM은 `echo=true`가 아닌 `/v1/completions`에서 `max_tokens=0`을 받지 않는다.
2. **추출기 = 실행 모델(32B) → 별도 Qwen3-8B 서버(:18002).** judge 베이스라인은 8B thinking on, D1은 실행 모델 전용 채점 서버(:18003, TP=1)에서 계측한다. 추출은 32B를 쓸 이유가 없고 실행 서버와 자원이 경합한다. AC-16의 "추출기도 같은 모델" 문구는 이로써 무효.
3. **"직접 답변" 후보 제거(스펙 v2.1–2.2) → `no_tool` = 1 − P(`<tool_call>`)로 복원.** 도구를 부르지 않는 스텝도 결정 지점이므로 후보 집합이 닫혀 있어야 분포가 정의된다.
4. **AC-20(D9 수식 정합성) 신설.** AIME 도메인에서 기록 대조 항목이 D2뿐이면 추론 오류를 잡을 수단이 없다.
5. **D9를 OPTIONAL → MUST 승격.** 위와 같은 이유. AIME 절반의 트레이스가 채점 대상에서 빠지는 것을 막는다.
6. **deepagents 내장 `task` 호출 → 이름 있는 래퍼 도구 호출(옵션 A′).** `task`는 대상 subagent를 인자(`subagent_type`)에 숨겨 D1이 handoff 결정을 잴 수 없다. 래퍼는 `task`의 state 규약(copy-in / merge-out)을 복제하며, `todos`는 그 규약상 비공유로 남는다.
7. **AC-11 "60건 전부" → 배치·컷 시점에 따른 n을 명시.** 시간 게이트가 배치 2를 포기시킬 수 있는 설계였기 때문이다(결과적으로 60건 전부 실행·라벨되었다).
8. **AC-10 "14:00 단일 컷" → 단계별 컷(계획 §8 타임라인) + 14:00 신규 코드 컷.** 단일 컷은 "무엇이 부분 완료인지"를 구분하지 못한다.
9. **AC-5 "결정 지점마다 분포" → 채점 완료 지점 + `d1_unscored.json` 유형별 카운트.** prefix 길이·경계 단언·시간 컷으로 미채점 지점이 남을 수 있다. 아울러 `user_sim`·`summarizer` 스텝은 결정 지점에서 제외하고, AC-4의 기록 항목에 도구 스키마·요약 직전 원문·시뮬레이터 호출·`finish_reason`을 명시했다.
10. **"분포 계산은 prefill 경로(`prompt_logprobs`)만" → decode 경로 teacher-forced 채점(`allowed_token_ids`) 단일 방법; 실행 기록 logprob은 렌더 정합 검사에만 사용.** 처음에는 prefill 경로를 정의로 두고 decode 경로를 동일성 게이트로 검증하려 했으나, prefill 경로도 기록과 같은 크기로 어긋나 게이트 자체가 기준이 될 수 없었다(§4.1.5).
11. **"τ-bench는 litellm + `OPENAI_API_BASE`" → raw httpx 사용자 시뮬레이터(`src/data/tau_user.py`).** litellm 경로로는 요청 본문·헤더 캡처와 thinking off / temperature 0 고정이 보장되지 않는다. 시스템 프롬프트와 `reset/step` 인터페이스는 원본을 따른다.
12. **출력 포맷 추가: 트레이스별 감사 보고서(P4b) + 시스템 단위 집계(P4c).** 사용자 결정(02:35). 통합 점수 대신 근거 포인터와 역할·엣지 단위 프로파일을 낸다.
13. **D2·D7 정의 보정(라벨 컷 이후, 05:02).** D2의 근거 풀이 도구 결과와 고객 발화만이어서 AIME 문제 문장의 값과 planner 지시문의 값을 "근거 없음"으로 세던 것을, 모델이 그 요청에서 입력으로 받은 것(system·user·tool 메시지; 자기 이전 발화 제외)을 근거로 인정하도록 고쳤다(평균 s 0.817 → 0.847, 48/793 스텝 변경). D7은 8B 추출기가 "Submitted 277." 같은 짧은 텍스트에서 값을 못 뽑아 fidelity 0이 되던 것을, 원문에 값이 문자 그대로 있으면 보존으로 치도록 고쳤다(report→planner fidelity 0 건수 69 → 52). 라벨은 탐지기를 보지 않고 달았으므로 정의 보정이지 라벨 맞춤이 아니며, 보정 전 출력은 `audit/d2_v1.jsonl`, `audit/d7_v1.jsonl`로 남겼다.
14. **D3 규칙 2(지시→행동) 사후 추가 (09-09 06:00).** 결과 검토 중 subagent의 no_tool이 구조상 "보고·복귀"임을 확인하고(260/260건 다음 스텝이 planner), 끝내기 전에 지시받은 작업을 수행했는지를 보는 결정적 규칙을 추가했다. 라벨을 보고 난 뒤의 추가이지만 규칙은 지시문 정규식 → 도구 군 매핑만 쓰고 라벨·정답을 입력으로 받지 않는다. 다른 항목의 수치는 변하지 않았다(`eval/metrics.md` 재생성).
15. **"근거 의존도"의 귀착.** 설계 인터뷰(스펙 Round 27–28)에서 제기된 "근거 의존도"는 "subagent가 도구 결과 없이 얼마나 근거 없는 주장을 하는가 = |1 − s|"로 확정되어 D2의 정의가 되었다. 같은 이름으로 논의된 반사실적 버전(근거 제거 시 결론 확률의 변화, Round 22 "의존도 × p(action)")은 "logprob으로 환각·추론을 판정하지 않는다"는 원칙에 따라 보조 피처로 보류됐고 미구현이다. 결과(§4.3)에 비추어 후자가 subagent 발언 층의 다음 후보다.
16. **D2 규칙 2(인자 근거) 사후 추가 (09-09 06:15).** 결과 검토에서 규칙 1이 환각성 라벨을 놓친 원인이 "값의 위치"(발언이 아닌 인자)임을 확인하고 추가했다. 규칙은 정규식과 문자열 대조만 쓰며 라벨·정답을 입력으로 받지 않는다. 공항 코드는 τ-bench `list_all_airports`의 도시명, 날짜는 자연어 표기를 근거로 인정한다. 다른 항목의 수치는 변하지 않았다.
17. **AIME를 보조 실험으로 격하 (09-09 06:30, 사용자 결정).** 계획은 두 도메인을 동격으로 두었으나(P3·AC-11), 결과 검토에서 AIME가 멀티에이전트 과제로 부적합함이 드러났다: solver가 풀이의 거의 전부를 하고 planner의 실질 결정이 적어(라벨된 planner 오류 6건) planner→subagent 분해가 형식적이고, 여러 셀이 airline과 반대 방향이다(planner D1 트레이스 max 0.34 vs 0.81). 본문(§0, §4.2 핵심 결과, §4.2.1–4.2.9, §4.3)은 airline만 보고하고, AIME 결과·D9·두 도메인 합산 셀은 §4.2.12에 참고로 둔다. 실행·라벨·채점은 그대로이고 모든 수치는 `eval/metrics.md`에 있다. D9 관련 이탈(항목 4·5)은 유지된다.
18. **D2·D9 모듈 삭제, 인자 근거 검사를 D3 규칙 3으로 이관 (09-09 06:25, 사용자 결정).** (1) D2 규칙 1(발언 값의 기록 근거)은 D3 규칙 1(숫자 주장 → 도구 근거)과 대상·판정이 겹치고 신호가 없어(airline subagent 0.47) 삭제했다. (2) D9(수식 정합성)는 AIME 전용이고 수식의 77 %가 판정불가라 삭제했다. (3) D2 규칙 2였던 도구 호출 인자 근거 검사는 결과가 있어(0.68, 정밀도 80 %) 유지하되 D3의 세 번째 규칙으로 옮겼다 — 코드 `src/audit/d3_args.py`, 출력 `audit/d3_args.jsonl`, 평가 항목 `D3_args`; 수치는 이관 전과 같다. 항목 13·15·16은 이력으로 남긴다. 삭제된 항목의 출력과 평가 이력은 `audit/_removed/`와 git 이력에 있다. 이로써 "값은 맞는데 결론이 틀린" 추론 오류 층은 이 연구에 탐지기가 없음을 §1.2·§4.3·한계에 명시했다.

## 부록 B. 재현

환경: 서버는 conda `math_infer`(vLLM 0.9.2), 나머지는 conda `agentbench`(Python 3.11, `requirements.txt`). **GPU는 1–4번만** 사용하며 포트는 18001–18003이다. 전체 절차는 README의 "Reproduce" 블록과 같다.

```bash
# 0. 설치 (agentbench 환경)
pip install -r requirements.txt
# 1. 서버 3대 (GPU 1-4)
bash scripts/serve_qwen32b.sh & bash scripts/serve_qwen8b.sh & bash scripts/serve_qwen32b_score.sh &
export OPENAI_BASE_URL=http://localhost:18001/v1 OPENAI_API_BASE=$OPENAI_BASE_URL OPENAI_API_KEY=dummy
python scripts/check_server.py && python scripts/probe_deepagents.py      # P1 / P1b 게이트
# 2. 데이터 + 실행
python -m src.data.tau --write && python -m src.data.aime --write
python -m src.run --domain airline --task 0 && python -m src.harness.validate runs/airline_000   # 스모크
python -m src.run --batch 1 --parallel 4 --resume      # 이후 --batch 2
# 3. 감사
python -m src.audit.d1 --check && python -m src.audit.d1 --all
python -m src.audit.d3 && python -m src.audit.d3_instruction && python -m src.audit.d3_args && python -m src.audit.d7 --stats
python -m src.audit.report && python -m src.audit.system_report
# 4. 라벨 + 평가
python -m src.eval.index && python -m src.eval.summarize   # 이후 labels/RUBRIC.md에 따라 labels/<run_id>.json 작성
python -m src.eval.labels --validate
python -m src.eval.metrics && python -m src.eval.thresholds && python -m src.eval.recovery
```

원본 트레이스(`runs/<id>/steps.jsonl`, `tool_calls.sqlite`, `fs/`)는 크기 때문에 커밋하지 않는다. `runs/index.csv`, `runs/<id>/summary.md`, `audit/`, `labels/`, `eval/`, 스크립트 전체는 커밋되어 있으므로 이 문서의 모든 표는 커밋된 산출물에서, 원본 트레이스는 위 스크립트에서 재생성된다.

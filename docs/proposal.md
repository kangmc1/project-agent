# 에이전트 시스템의 handoff 안정성: 압축·인수인계 경계에서 정보가 깨지는 정도를 수치화하는 벤치마크와 파이프라인

> 제출용 본문 초안 (v0.2, 2026-09-08 17:20). [ ] 표시는 실험 결과 대기.

## 0. 한 장 요약
- **문제**: 에이전트 시스템은 문맥이 유일한 상태이고, 긴 작업일수록 문맥을 압축하고 다른 에이전트에 넘긴다. 이 경계에서 제약과 사실이 빠지거나 추측이 사실로 굳고, 원본이 사라져 복구되지 않는다. 2026년 프로덕션 사고(OpenClaw 받은편지함 삭제)의 원인이 compaction에서의 제약 소실이었고, 통제 실험에서는 통상적 압축이 차단 조건을 100% 비활성화했다(Constraint Weakening).
- **기존 탐지의 한계**: LLM judge는 궤적 하나를 읽고 "이상한가"를 묻는다. 스텝 위치 특정 11~33%, false success AUROC 0.65, 프로덕션 결함 23개 중 0개 포착, 정상 궤적 42~50% 과잉 탐지. 탐지기 자체를 믿을 수 없다는 것이 문제의 일부다(D5).
- **제안**: 탐지기의 정확도를 묻는 대신 **시스템의 handoff 안정성**을 잰다. 검증 가능한 의무(제약·사실·미확인·금지)를 심어 둔 합성 시나리오를 오케스트레이터-워커 워크플로우에 통과시키고, 경계마다 의무의 생존을 규칙으로 판정한다. 정답을 우리가 심었으므로 judge가 필요 없다. 개입 변수는 handoff 가시성(전체 기록 vs 요약만), 압축 포맷(자유 서술 vs `unverified`를 명시하는 구조화 JSON), 경계 검사기 유무.
- **행동 분포 기반 신호**: 오케스트레이터의 행동을 "다음 에이전트 선택"(4지선다)으로 정의하고 logprobs에서 분포를 직접 읽는다. 압축 전후 정책 발산(JSD)과 정책 벡터 위의 선형 프로브로 "정답 없이 손실을 예측할 수 있는가"를 시험한다(D3).
- **기대효과**: 관측 제품에 "이 구성은 압축 N번까지 의무 생존 90%"라는 안정성 등급과, 경계에서 무엇이 사라졌는지 보여 주는 계기판. 로그 계약(경계 전후 문맥, 도구 원시 출력, 행동 영수증)을 제품 요구사항으로 도출.

## 1. 배경 (Background)
### 1.1 현재의 에이전트 시스템은 어떻게 작동하는가
(`design/04_simple_framing.md` §1) 루프 / 문맥이 유일한 상태 / 압축·외부 메모리·분할 / 도구 결과는 신뢰 불가 텍스트 / 산업 배치에서 병렬·분할이 늘수록 압축과 메시지 교환이 는다(`related_work/08`). 오케스트레이터-워커 구조는 도구를 에이전트로 바꾼 ReAct이며, Magentic-One·Anthropic 리서치 시스템·Claude Code 서브에이전트·Copilot Studio가 이 형태다.

### 1.2 무엇이 고장 나는가 (세 증거원 교차)
(`design/03_problem_landscape.md`) P1 오류 누적, P2 미검증 진행·false success, P3 관측 오독·도구 오용, P4 압축·handoff 상태 소실, P5 무단·파괴적 행동, P6 인젝션, P7 멀티에이전트 증폭. P4는 통제 실험(R)과 실제 사고(P)가 같은 메커니즘을 지목하는 항목이며, 오류의 출발점이라기보다 **굳히고 퍼뜨리는 통로**다.

### 1.3 기존 기술로 탐지되는 것과 안 되는 것
(`design/04_simple_framing.md` §3~4) 형식·인자 오류·최종 실패는 잡힘. 과정상 결함(D1 false success, D2 압축 소실, D3 초반 오류, D4 근거 없는 주장)은 judge가 주된 도구이나 신뢰도 낮음(D5). 프로덕션 로그는 입력이 없음(D6).

### 1.4 연구 세부 주제와 차별점
- **주제**: 압축·handoff 경계에서의 정보 훼손을 "시스템 안정성"으로 수치화하는 벤치마크·파이프라인.
- **차별점(3차 검증된 문장만)**: (i) 판정을 judge에 맡기지 않고 심어 둔 의무의 생존으로 측정(정답 by construction), (ii) 생존을 압축 횟수·가시성·포맷·검사기의 함수로 같은 축에서 비교, (iii) 행동을 유한 집합으로 정의해 정책 분포를 직접 읽고 손실과의 관계를 시험, (iv) 오케스트레이터-워커 표준 구조를 그대로 재현. 가장 가까운 연구(Bound-Handoff: 프라이버시 마커, Constraint Weakening: 안전 차단 조건, AgentAsk: 수학/코드 메시지 결함)는 단일 hop·특정 도메인에 머묾.

## 3. 제안 (Methodology & Benchmark Proposal)
### 3.1 정의
- **handoff**: 송신 에이전트 S가 만든 명시적 산출물 A가 수신 에이전트 R의 입력 문맥을 구성하고, 이후 R이 S보다 먼저 결정을 내리는 사건. 위험은 R이 S의 문맥을 얼마나 볼 수 있는가(정보 비대칭)로 결정된다.
- **의무** o: 하류 에이전트가 반드시 알거나 지켜야 하는 항목. 유형 constraint / verified_fact / open_question / prohibition. 각 의무는 핵심 값(숫자·id·이름·날짜)을 가진다.
- **생존**: preserved / altered(값이 바뀜) / absent / promoted(미확인이 사실로 승격). 규칙 매처가 핵심 값의 존재와 헤지 표현·구역(또는 JSON status)으로 판정한다.

### 3.2 워크플로우 (사적 출처를 가진 오케스트레이터-워커)
- 역할: Orchestrator(계획·지시·압축·최종 답) / Researcher(**출처를 읽을 수 있는 유일한 역할**, 사실·조건을 값과 함께 보고, 없으면 "UNAVAILABLE") / Executor(state·보고만으로 구체 행동 초안, 없으면 "MISSING") / Verifier(state의 제약·금지·사실과 대조, APPROVE|REVISE). 모두 같은 Qwen3-8B, 시스템 프롬프트만 다름. 정의 전체는 `docs/SETUP.md`.
- **행동 = 다음 에이전트 선택**(4지선다) + 에이전트별 행동 유형(유한) + 대상·지시문. 분포는 guided-choice 첫 토큰 logprobs로 한 번에 읽고, 상태만 보고 잰 분포(정책 불확실성)와 짧은 평가문 뒤의 실제 결정을 분리 기록.
- 경계 네 가지와 측정(`STATUS.md` §3): B1 지시(가시성 shared|summary), B2 반환(보고 속 날조 값, Verifier 판정), B3 압축(대화록 단어 수 > 예산 시; free|json; 가드; 의무 생존·승격, 압축 전후 정책 JSD), B4 최종(제약 보존, 금지 위반, 승격, 날조).
- 압축은 별도 에이전트가 아니라 **오케스트레이터의 호출 하나**다(결정·압축·최종 답이 모두 오케스트레이터 역할; Magentic-One의 재계획, Claude Code의 auto-compact와 동일). 압축 시점에 원본 대화록과 보고는 모두 폐기되고 새 state만 남는다(에이전트에게도, 오케스트레이터의 최근 보고 창에도 남지 않음).
- handoff 횟수는 강제하지 않는다. 체인 스트레스에서는 압축 횟수 K를 통제하고, 워크플로우에서는 **압축 예산**으로 횟수를 간접 조절하며 경계 단위(압축 1회당)로 정규화해 측정한다.
- 정보 비대칭: 시나리오 대화록은 Researcher만 읽는 **사적 출처**다(실제 시스템에서 worker만 갖는 도구 결과·문서에 대응). 오케스트레이터·Executor·Verifier는 Researcher의 보고를 통해서만 사실을 얻는다. 외부 도구·world 시뮬레이션은 없으므로 관측 오류·환경 실패는 재현하지 않는다(측정값은 전달 손실의 하한).
- 최종 손실은 **획득 실패**(출처의 사실이 보고로 들어오지 못함)와 **전달 손실**(획득 후 압축·초안·최종에서 사라짐)로 나눠 보고한다. 벤치마크의 주 대상은 후자다.
- 심어 둔 의무 목록은 어느 에이전트에게도 주지 않는다. 가드는 압축 직전 팀이 실제로 갖고 있던 항목만 복구한다.

### 3.3 안정성 지표 (D5의 답)
- 압축 k회 뒤 생존율 S(k) = preserved 비율, 반감 압축 횟수 k½, 승격율, 최종 답의 제약 보존·금지 위반·날조율, Verifier REVISE율, 토큰.
- 판정은 심어 둔 항목의 존재(닫힌 질문)이므로 judge 불필요 → 탐지기 신뢰도 문제를 우회.

### 3.3b 두 설정: 고정 task와 task 미지
본 실험은 과제와 팀 구성이 고정된 설정이다. 과제 유형을 모르는 설정에서는 시작 시 오케스트레이터가 카탈로그에서 에이전트·스킬 후보군을 선정하고 카탈로그 문구를 문맥에서 제거하는 **B0 선정 handoff**가 추가된다(Captain-Agent의 팀 구성, tool search, Copilot Studio의 분할과 대응). B0에서 필요한 능력이 빠지면 실행 중 복구가 불가능하므로 B3와 같은 종류의 경계이며, 시나리오에 required_capability를 심어 선정 손실률로 측정한다(확장 실험). 실행 중 행동 공간이 고정되므로 §3.5의 분포·프로브가 그대로 적용된다. 이는 §1의 "task-specific / task 판단 모듈 / general" 구분에 대응한다: 고정 task = task-specific, B0 = task 판단 모듈, 역할 슬롯 프로브 = general.

### 3.4 개입 변수
- 가시성 (B1): shared vs summary.
- 압축 포맷 (B3, D2): 자유 서술 vs 구조화 JSON — 키 constraints/verified_facts/open_questions/prohibitions/goal, 값 없으면 `"unverified"`/`"extraction_failed"` 명시.
- 경계 검사기 (B3): 압축 직후 매처로 의무 생존 확인, 소실·변조·승격 항목 재삽입.
- (확장) 폭: 병렬 에이전트 1 vs 3 (fan-in 상충).

### 3.5 행동 분포 신호 (D3)
- 라운드별 정책 엔트로피, 압축 전후 정책 JSD(정답 없이 계산 가능한 손실 신호 후보).
- **선형 프로브**: 입력 [p(4), 엔트로피, 상위 1·2위 차, 라운드, 단어 수, JSD] → 다음 압축에서 손실 여부. 시나리오 단위 교차검증, AUROC. 행동 수가 시스템마다 다르면 순열 불변 요약치 또는 역할 슬롯으로 일반화. (선택) 결정 토큰 시점 은닉 상태 프로브.

### 3.6 파이프라인
1. 시나리오 생성기: task + 대화록 + typed 의무 8개, 규칙 검증 (`scenarios/`)
2. 규칙 매처 + 검증 스크립트 (`matching.py`, `scripts/validate_matcher.py`)
3. 워크플로우 엔진 + 그리드 러너 (`workflow/`, `scripts/run_workflow.py`)
4. 체인 스트레스(압축만 K회 반복) (`chain/stress.py`, `scripts/run_stress.py`)
5. 집계·프로브 (`eval/`)
6. 로그 계약(D6) — 워크플로우가 남기는 기록 스키마가 곧 제품 요구사항:
```
round      : r, state_id, 대화록 단어 수
action     : next_agent, action_type, target, instruction, p(선택지별), entropy
report     : agent, 보고 원문, 날조 후보 값, Verifier 판정
tool_call  : (도구가 있는 시스템) 도구명, 인자, 원시 결과 전문, 영수증 id   ← 문맥에서 지워도 로그에는 남김
compression: 전 상태, 후 상태, 포맷, 단어 수, 정책 JSD, (실험에서만) 의무 생존
final      : 최종 답, 제약·금지·날조 검사
```
   실험에서는 JSONL 한 줄/실행이면 충분하고, 프로브는 이 기록에서 학습한다. 시스템마다 에이전트·도구가 다르면 "역할 유형 → 에이전트" 매핑을 레지스트리로 두어 프로브의 역할 슬롯을 재사용한다.
